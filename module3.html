মডিউল ৩ · Virtualizing Memory

Memory ও
Virtual Memory

প্রতিটা প্রোগ্রাম মনে করে পুরো RAM শুধু তার — শূন্য থেকে শুরু, বিশাল, একান্ত নিজের। অথচ বাস্তবে ডজন ডজন প্রোগ্রাম একই সীমিত RAM ভাগ করছে। এই মায়াজাল কীভাবে তৈরি হয়, byte ধরে ধরে দেখবো।

০০

শুরুর কথা

orientation

মডিউল ২-তে দেখলাম CPU কীভাবে virtualize হয় (একটা CPU, অনেক process)। এবার virtualization-এর দ্বিতীয় অর্ধেক — memory। একটা RAM, অথচ প্রতিটা process পায় নিজের সম্পূর্ণ একান্ত address space।

🧭 এই মডিউল কোথায় ফিট করে মডিউল ২ (process) + মডিউল ৩ (memory) মিলে OSTEP-এর প্রথম স্তম্ভ Virtualization সম্পূর্ণ হয়। এখানকার মূল প্রশ্ন: দুটো প্রোগ্রাম যদি দুজনেই 0x1000 ঠিকানায় ডেটা রাখতে চায়, তারা কি একে অপরেরটা মুছে দেবে? উত্তর — না, আর সেই "না"-এর পেছনের কৌশলটাই এই মডিউল।
🛠 পরিবেশ আগের মতোই Linux/WSL2 + gcc। এই মডিউলে pointer আর memory নিয়ে অনেক কাজ, তাই gdb (debugger) ও valgrind (memory leak ধরার টুল) ইনস্টল রাখলে ভালো: sudo apt install gdb valgrind
০১

কেন Virtual Memory?

why-virtual-memory

সমস্যাটা আগে বুঝি। কল্পনা করুন virtual memory নেই — প্রতিটা প্রোগ্রাম সরাসরি physical RAM-এর ঠিকানা ব্যবহার করছে। কী কী ভুল হতে পারে?

⚠️ Virtual memory ছাড়া তিনটা বিপর্যয় ১. নিরাপত্তা নেই: প্রোগ্রাম A সরাসরি ঠিকানা 0x2000-এ লিখলে, সেটা যদি প্রোগ্রাম B-র ডেটা হয়, B ধ্বংস হয়ে যাবে। যেকোনো প্রোগ্রাম যেকোনো প্রোগ্রামের (এমনকি OS-এর) memory পড়তে-লিখতে পারবে।
২. জটিলতা: প্রতিটা প্রোগ্রাম লেখার সময় জানতে হবে RAM-এর কোন অংশ খালি — কিন্তু সেটা তো নির্ভর করে আর কী কী চলছে তার উপর, যা আগে থেকে জানা অসম্ভব।
৩. সীমাবদ্ধতা: RAM-এর চেয়ে বড় প্রোগ্রাম চালানো যাবে না।

সমাধান — একটা বিভ্রম (abstraction)

Virtual memory প্রতিটা process-কে একটা মিথ্যা কিন্তু সুবিধাজনক ছবি দেয়: "পুরো memory শুধু তোমার, ০ থেকে শুরু, বিশাল ও একটানা।" প্রোগ্রাম এই virtual ঠিকানা ব্যবহার করে, আর OS + হার্ডওয়্যার নীরবে সেটাকে আসল physical ঠিকানা-য় অনুবাদ করে দেয়।

💡 তিনটা সমস্যার সমাধান একসাথে নিরাপত্তা: A-র virtual ঠিকানা কখনো B-র physical memory-তে ম্যাপ করা হয় না, তাই A চাইলেও B-কে ছুঁতে পারে না। সরলতা: প্রতিটা প্রোগ্রাম ধরে নেয় সে ০ থেকে শুরু, বাকি কী চলছে জানার দরকার নেই। সীমা অতিক্রম: virtual space RAM-এর চেয়ে বড় হতে পারে — বাকিটা disk-এ (swap, পরে দেখবো)।
🧠 যাচাই করুন
দুটো প্রোগ্রাম দুজনেই 0x1000 ব্যবহার করলে সংঘর্ষ হয় না কেন?

কারণ ওটা virtual ঠিকানা। OS দুটো process-এর একই virtual ঠিকানাকে RAM-এর ভিন্ন physical জায়গায় ম্যাপ করে। তাই কোনো সংঘর্ষ নেই।

Virtual memory কীভাবে নিরাপত্তা দেয়?

এক process-এর virtual ঠিকানা কখনো আরেক process-এর physical memory-তে ম্যাপ করা হয় না। তাই একটা process অন্যের (বা OS-এর) memory পড়তে বা নষ্ট করতে পারে না।

০২

Address Translation

address-translation

মূল প্রশ্ন: একটা virtual ঠিকানা কীভাবে physical ঠিকানায় বদলায়? সবচেয়ে সরল ধারণা দিয়ে শুরু করি, তারপর দেখবো কেন সেটা যথেষ্ট নয়।

সরলতম উপায় — Base + Bound

প্রতিটা process-কে RAM-এর একটা একটানা টুকরো দেওয়া হয়। দুটো register রাখা হয়: base (টুকরোটা কোথায় শুরু) আর bound (কতটা বড়)। অনুবাদ সহজ:

physical ঠিকানা = virtual ঠিকানা + base
যদি virtual ঠিকানা >= bound হয় → অবৈধ (protection fault)
🏢 উপমা — অ্যাপার্টমেন্ট নম্বর আপনি বললেন "ফ্ল্যাট ৫"। কিন্তু কোন বিল্ডিং? বিল্ডিংটা যদি ১০০ নম্বর থেকে শুরু হয় (base), তাহলে আপনার আসল ঠিকানা ১০৫। প্রতিটা process-এর নিজের "বিল্ডিং" (base), তাই সবার "ফ্ল্যাট ৫" আলাদা আসল জায়গায় পড়ে। আর bound নিশ্চিত করে আপনি নিজের বিল্ডিংয়ের বাইরের ফ্ল্যাট চাইতে পারবেন না।
⚠️ Base+bound-এর বড় সমস্যা — fragmentation প্রতিটা process-কে একটা একটানা বড় টুকরো দিতে হয়। কিন্তু process আসে-যায়, ফলে RAM-এ ছোট ছোট ফাঁকা টুকরো তৈরি হয় — মোট খালি জায়গা যথেষ্ট, কিন্তু কোনো একটানা টুকরো যথেষ্ট বড় নয়। একে বলে external fragmentation। আর process-এর পুরো address space (heap/stack-এর জন্য সংরক্ষিত জায়গা সহ) RAM-এ রাখতে হয়, যদিও বেশিরভাগ অব্যবহৃত — অপচয়। এই সমস্যার সমাধানই paging।
🧠 যাচাই করুন
base = 3000 হলে virtual ঠিকানা 50 কোথায় ম্যাপ হবে?

Physical ঠিকানা 3050 (50 + 3000)। আর bound-এর বেশি চাইলে protection fault।

External fragmentation কী?

RAM-এ যথেষ্ট মোট খালি জায়গা আছে, কিন্তু ছড়ানো-ছিটানো ছোট টুকরোয়, তাই একটা বড় একটানা বরাদ্দ দেওয়া যায় না। base+bound-এর মূল দুর্বলতা।

০৩

Paging — টুকরো টুকরো করে সমাধান

paging

Paging হলো আধুনিক memory ব্যবস্থাপনার হৃদয়। মূল ধারণা সহজ কিন্তু শক্তিশালী: memory-কে একটানা বড় টুকরোয় না ভেবে, সমান আকারের ছোট ব্লকে ভাগ করো।

📦 দুটো মূল শব্দ Page: virtual memory-র একটা fixed-size ব্লক (সাধারণত ৪ KB)।
Frame: physical RAM-এর একটা সমান আকারের ব্লক।
কাজটা সহজ হয়ে যায় — যেকোনো page যেকোনো frame-এ বসতে পারে। আর সব সমান আকারের বলে external fragmentation নেই!
📚 উপমা — বইয়ের পাতা তাকে রাখা একটা বই (process) টেবিলে একটানা রাখতে বড় জায়গা লাগে। কিন্তু বইটার প্রতিটা পাতা (page) যদি আলাদা করে ফেলেন, তাহলে তাকের যেকোনো খালি খোপে (frame) যেকোনো পাতা রাখতে পারেন — ছড়িয়ে-ছিটিয়ে থাকলেও চলে। শুধু একটা সূচি (page table) রাখতে হবে "কোন পাতা কোন খোপে"।

Page Table — অনুবাদের মানচিত্র

প্রতিটা process-এর একটা page table থাকে — যা বলে কোন virtual page কোন physical frame-এ আছে। একটা virtual ঠিকানা দুই ভাগে ভাঙা হয়:

🔬 গভীরে — offset কেন অপরিবর্তিত? ধরুন page size ৪ KB (৪০৯৬ byte = ২¹²)। তাহলে ঠিকানার নিচের ১২ বিট হলো offset (page-এর ভেতরে অবস্থান), আর বাকি উপরের বিটগুলো VPN। যেহেতু page আর frame একই আকারের, page-এর ভেতরে যতটা দূরে, frame-এর ভেতরেও ঠিক ততটাই দূরে — তাই offset বদলানোর দরকার নেই। শুধু "কোন page → কোন frame" অংশটুকু অনুবাদ হয়। এই কারণেই page size সবসময় ২-এর ঘাত — যাতে বিট ভাগ করা সহজ হয়।

page table-এর প্রতিটা এন্ট্রিতে (PTE) frame নম্বর ছাড়াও কিছু গুরুত্বপূর্ণ বিট থাকে:

বিটমানে
Validএই page কি ব্যবহৃত? (নাহলে অ্যাক্সেসে fault)
Protection (R/W/X)পড়া / লেখা / চালানো যাবে?
Presentpage কি এখন RAM-এ, নাকি disk-এ (swap)?
Dirtypage কি বদলানো হয়েছে? (swap করার সময় লাগে)
Accessedসম্প্রতি ব্যবহৃত? (replacement সিদ্ধান্তে লাগে)
🧠 যাচাই করুন
Paging কেন external fragmentation দূর করে?

কারণ সব page ও frame একই আকারের। যেকোনো page যেকোনো খালি frame-এ বসে, তাই "যথেষ্ট বড় একটানা টুকরো" খোঁজার সমস্যাই নেই।

Page size ৪ KB হলে offset কত বিট?

১২ বিট (২¹² = ৪০৯৬)। বাকি উপরের বিটগুলো VPN।

PTE-র valid বিট ০ থাকলে অ্যাক্সেস করলে?

একটা fault হয় (invalid access) — সাধারণত segmentation fault, কারণ ওই virtual page ব্যবহারই হচ্ছে না।

০৪

TLB — অনুবাদ দ্রুত করা

translation-lookaside-buffer

Paging-এর একটা লুকানো খরচ আছে। প্রতিটা memory অ্যাক্সেসে আগে page table দেখতে হয় (RAM-এ), তারপর আসল ডেটা আনতে হয় (আবার RAM-এ)। অর্থাৎ প্রতিটা অ্যাক্সেস দ্বিগুণ ধীর! এই সমস্যার সমাধান TLB।

📇 উপমা — বারবার ব্যবহৃত নম্বর মুখস্থ ফোনবুকে (page table) নম্বর খোঁজা ধীর। কিন্তু যে কয়েকটা নম্বর আপনি বারবার ডায়াল করেন, সেগুলো মুখস্থ হয়ে যায় (TLB)। পরেরবার ফোনবুক না খুলেই ডায়াল করেন। TLB হলো CPU-র ভেতরের একটা ছোট, অতি-দ্রুত cache যা সাম্প্রতিক অনুবাদগুলো মনে রাখে।

TLB সহ অনুবাদের প্রবাহ

💡 কেন TLB এত ভালো কাজ করে — Locality প্রোগ্রাম সাধারণত পরপর কাছাকাছি ঠিকানা ব্যবহার করে (একটা array-র উপর লুপ, বা একই function বারবার)। একে বলে locality of reference। তাই একটা page-এর অনুবাদ একবার TLB-তে এলে, পরের অনেক অ্যাক্সেস সেই একই page-এ পড়ে — সব HIT। এজন্যই ছোট TLB (হয়তো ৬৪-১৫৩৬ এন্ট্রি) থাকা সত্ত্বেও hit rate সাধারণত ৯৯%+।
⚠️ TLB ও performance — বাস্তব প্রভাব TLB miss ব্যয়বহুল। যে প্রোগ্রাম memory-তে এলোমেলোভাবে (কম locality) অ্যাক্সেস করে — যেমন বিশাল hash table বা linked list এলোমেলো ঘোরা — তার TLB miss বেশি হয়, তাই ধীর চলে। এজন্যই cache-friendly ডেটা স্ট্রাকচার (array, পাশাপাশি memory) প্রায়ই linked structure-এর চেয়ে দ্রুত, যদিও big-O একই। পারফরম্যান্স টিউনিং-এ এটা বড় বিবেচনা।
🧠 যাচাই করুন
TLB না থাকলে প্রতিটা memory অ্যাক্সেসে কী সমস্যা?

প্রতিবার আগে page table (RAM-এ) দেখতে হতো, তারপর আসল ডেটা (RAM-এ) — অর্থাৎ প্রতিটা অ্যাক্সেস দ্বিগুণ ধীর হতো।

Array কেন প্রায়ই linked list-এর চেয়ে দ্রুত, একই big-O সত্ত্বেও?

Array-র উপাদান পাশাপাশি memory-তে, তাই ভালো locality — কম TLB miss ও কম cache miss। Linked list এলোমেলো ছড়ানো, তাই বেশি miss, ধীর।

০৫

Multi-level Page Table

multi-level-page-tables

একটা সমস্যা রয়ে গেছে। page table নিজেই তো memory খায়! আর সেটা আশ্চর্যজনকভাবে বড় হতে পারে। এই অধ্যায় সেই সমস্যা ও তার মার্জিত সমাধান।

⚠️ সমস্যা — page table বিশাল ৩২-বিট সিস্টেমে (৪ GB virtual space), page size ৪ KB হলে, মোট page সংখ্যা = ২²⁰ = প্রায় ১০ লক্ষ। প্রতিটা PTE যদি ৪ byte, তাহলে একটা process-এর page table = ৪ MB। প্রতিটা process-এর জন্য! ১০০টা process চললে শুধু page table-এই ৪০০ MB। আর বেশিরভাগ process তো পুরো ৪ GB ব্যবহারই করে না — বিশাল অংশ ফাঁকা, তবু তার জন্য এন্ট্রি রাখতে হচ্ছে।

সমাধান — গাছের মতো স্তরে স্তরে

একটা বিশাল সমতল টেবিলের বদলে, page table-কে স্তরে স্তরে ভাঙা হয় — একটা page directory যা ছোট ছোট page table-এর দিকে নির্দেশ করে। মূল চালাকি: যে অংশ ব্যবহৃত হয় না, তার জন্য কোনো নিচের স্তরের টেবিল বানানোই হয় না।

🔬 গভীরে — বাস্তবে কত স্তর? আধুনিক ৬৪-বিট x86 (x86-64) সাধারণত ৪ স্তর ব্যবহার করে (কিছু নতুন সিস্টেমে ৫)। virtual ঠিকানা ভাগ হয় কয়েকটা index + একটা offset-এ, প্রতিটা index এক স্তরের টেবিলে নামায়। খরচ: TLB miss হলে অনুবাদের জন্য এখন ৪ বার memory দেখতে হয় (প্রতি স্তরে একবার)! এজন্যই TLB আরও গুরুত্বপূর্ণ হয়ে ওঠে — multi-level page table memory বাঁচায় কিন্তু miss-এর খরচ বাড়ায়, আর TLB সেই খরচ আড়াল করে। সুন্দর ভারসাম্য।
🧠 যাচাই করুন
Multi-level page table কীভাবে memory বাঁচায়?

Virtual space-এর যে অংশ ব্যবহৃত হয় না, তার জন্য নিচের স্তরের টেবিল বানানোই হয় না। বিশাল ফাঁকা address space-এর জন্য শুধু কয়েকটা directory এন্ট্রি লাগে, পুরো টেবিল নয়।

Multi-level-এ TLB miss কেন বেশি ব্যয়বহুল?

প্রতিটা স্তরের টেবিল আলাদাভাবে দেখতে হয়। ৪-স্তরে একটা অনুবাদে ৪ বার memory অ্যাক্সেস লাগে — তাই TLB hit আরও বেশি জরুরি হয়ে ওঠে।

০৬

Page Fault ও Swap

page-fault-and-swap

এবার virtual memory-র সবচেয়ে শক্তিশালী কৌশল: RAM-এর চেয়ে বেশি memory ব্যবহার করা। কীভাবে? যে page গুলো এই মুহূর্তে লাগছে না, সেগুলো disk-এ সরিয়ে রাখা।

🗄️ উপমা — ডেস্ক আর ফাইল ক্যাবিনেট আপনার ডেস্ক (RAM) ছোট, সব ফাইল রাখা যায় না। যেগুলো এখন কাজে লাগছে সেগুলো ডেস্কে, বাকিগুলো ফাইল ক্যাবিনেটে (disk/swap)। হঠাৎ ক্যাবিনেটের একটা ফাইল দরকার হলে, ডেস্কের কোনো একটা সরিয়ে সেটা এনে রাখেন। এই "ক্যাবিনেট থেকে আনা"-র মুহূর্তটাই page fault।

Page Fault-এ কী ঘটে

CPU একটা virtual ঠিকানা চাইল, কিন্তু page table বলছে page টা এখন RAM-এ নেই (present বিট = ০, disk-এ আছে)। তখন:

  1. হার্ডওয়্যার একটা page fault (একধরনের trap) তোলে, OS-এ নিয়ন্ত্রণ যায়
  2. OS disk-এ খুঁজে page টা বের করে
  3. RAM-এ একটা খালি frame বাছে (না থাকলে একটা page সরায় — পরের অধ্যায়)
  4. disk থেকে page টা সেই frame-এ আনে
  5. page table আপডেট করে (present = ১)
  6. যে instruction fault করেছিল, সেটা আবার চালায় — এবার সফল হয়
💡 fault মানে সবসময় ভুল নয় "Fault" শুনলে ভুল মনে হয়, কিন্তু page fault একটা স্বাভাবিক ও প্রত্যাশিত ঘটনা। এটা OS-কে সুযোগ দেয় নীরবে disk থেকে ডেটা আনার। প্রোগ্রাম টেরও পায় না — শুধু সেই একটা অ্যাক্সেস একটু ধীর হয়। এই কৌশলে একটা প্রোগ্রাম RAM-এর চেয়ে অনেক বড় হতে পারে; শুধু সক্রিয় অংশটুকু RAM-এ থাকে।
⚠️ Thrashing — যখন সব ভেঙে পড়ে Disk RAM-এর চেয়ে হাজার গুণ ধীর। যদি একসাথে চলা প্রোগ্রামগুলোর মোট সক্রিয় memory (working set) RAM-এর চেয়ে বেশি হয়, তাহলে OS ক্রমাগত page swap করতে থাকে — একটা আনতে গিয়ে আরেকটা সরায়, যেটা সরাল সেটাই আবার লাগে। এই অবস্থায় CPU-র বেশিরভাগ সময় শুধু disk I/O-তে যায়, আসল কাজ প্রায় থেমে যায়। একে বলে thrashing — কম্পিউটার হঠাৎ ভয়ংকর ধীর হয়ে গেলে প্রায়ই এটাই কারণ (RAM কম, বেশি প্রোগ্রাম)।
🧠 যাচাই করুন
Page fault কি সবসময় একটা error?

না — এটা প্রায়ই স্বাভাবিক। OS এই সুযোগে disk থেকে দরকারি page RAM-এ আনে। প্রোগ্রাম চলতে থাকে, শুধু ওই অ্যাক্সেসটা ধীর হয়।

Thrashing কেন হয়?

সক্রিয় প্রোগ্রামগুলোর মোট working set RAM-এর চেয়ে বড় হলে। তখন OS অবিরাম page swap করে, CPU-র সময় প্রায় সব disk I/O-তে যায়, আসল কাজ থেমে যায়।

০৭

Page Replacement

page-replacement

RAM ভরে গেছে, নতুন একটা page আনতে হবে — কিন্তু কোন পুরনো page সরাবেন? এই সিদ্ধান্ত গুরুত্বপূর্ণ, কারণ ভুল page সরালে সেটা আবার সাথে সাথে লাগবে (আরেকটা fault)।

মূল অ্যালগরিদমগুলো

নীতিধারণাসমস্যা
Optimal (OPT)যে page সবচেয়ে দূর ভবিষ্যতে লাগবে, সেটা সরাওভবিষ্যৎ জানা অসম্ভব — শুধু তুলনার মাপকাঠি
FIFOযে page সবচেয়ে আগে এসেছে, সেটা সরাওবহু ব্যবহৃত page-ও সরে যেতে পারে
LRUযে page সবচেয়ে বেশিক্ষণ ব্যবহৃত হয়নি, সেটা সরাওনিখুঁত করা ব্যয়বহুল
ClockLRU-র সস্তা আনুমানিক রূপনিখুঁত নয়, কিন্তু যথেষ্ট ভালো
💡 LRU কেন যুক্তিসঙ্গত — আবারও Locality LRU-র ধারণা: যা সম্প্রতি ব্যবহৃত হয়েছে, তা আবার শিগগির লাগবে (locality)। তাই যেটা অনেকক্ষণ ব্যবহার হয়নি, সেটা সরানোই নিরাপদ। বাস্তবে বেশিরভাগ প্রোগ্রামে এটা ভালো কাজ করে। কিন্তু নিখুঁত LRU-তে প্রতিটা অ্যাক্সেসে টাইমস্ট্যাম্প আপডেট করতে হয় — ব্যয়বহুল। তাই বাস্তব OS "Clock" (বা তার উন্নত রূপ) ব্যবহার করে।
🔬 গভীরে — Clock অ্যালগরিদম সব page একটা বৃত্তাকার তালিকায় (ঘড়ির মতো)। প্রতিটা page-এর একটা use বিট (accessed বিট) আছে — ব্যবহৃত হলে হার্ডওয়্যার ১ করে দেয়। একটা "কাঁটা" ঘুরতে থাকে: যে page-এ use বিট = ১, সেটাকে ০ করে এগিয়ে যায় (দ্বিতীয় সুযোগ দেয়); যে page-এ use বিট = ০ পায়, সেটাই সরায়। এভাবে সাম্প্রতিক ব্যবহৃত page বেঁচে যায়, আর পুরোটা টাইমস্ট্যাম্প রাখার খরচ ছাড়াই LRU-র কাছাকাছি ফল পাওয়া যায়। মার্জিত!
⚠️ Belady's Anomaly — একটা অদ্ভুত ব্যাপার সাধারণত বেশি RAM = কম page fault, তাই না? FIFO-তে সবসময় নয়! কিছু ক্ষেত্রে বেশি frame দিলে FIFO-তে page fault বেড়ে যায় — একে বলে Belady's Anomaly। এটা FIFO-র একটা দুর্বলতা প্রকাশ করে। LRU-তে এই সমস্যা নেই (এগুলোকে "stack algorithm" বলে)। পরীক্ষায় ও ইন্টারভিউতে এটা একটা প্রিয় প্রশ্ন।
🧠 যাচাই করুন
Optimal অ্যালগরিদম বাস্তবে ব্যবহার করা যায় না কেন?

এর জন্য ভবিষ্যৎ জানা লাগে (কোন page কখন লাগবে), যা অসম্ভব। এটা শুধু অন্য অ্যালগরিদম কতটা ভালো তা মাপার তাত্ত্বিক মাপকাঠি।

Clock অ্যালগরিদম কীভাবে সস্তায় LRU-র কাছাকাছি যায়?

প্রতিটা page-এর একটা use বিট রাখে। কাঁটা ঘুরে use বিট ১ পেলে ০ করে দ্বিতীয় সুযোগ দেয়, ০ পেলে সরায়। টাইমস্ট্যাম্প রাখার ব্যয় ছাড়াই সাম্প্রতিক page বাঁচে।

Belady's Anomaly কী?

FIFO-তে কখনো কখনো বেশি frame দিলে page fault বেড়ে যায় — স্বজ্ঞার বিপরীত। LRU-জাতীয় অ্যালগরিদমে হয় না।

০৮

প্রজেক্ট — নিজের malloc লিখুন

build-malloc

এই মডিউলের সব ধারণা কাজে লাগানোর সময়। malloc/free আপনি হাজারবার ব্যবহার করেছেন — এবার নিজে লিখে দেখবেন heap কীভাবে কাজ করে, fragmentation কী, আর memory ব্যবস্থাপনা কেন কঠিন।

🎯 malloc আসলে কী করে OS প্রোগ্রামকে একটা বড় heap দেয় (brk/sbrk বা mmap দিয়ে)। malloc-এর কাজ সেই বড় ব্লকটাকে ছোট ছোট টুকরোয় ভাগ করে চাহিদামতো দেওয়া, আর free-তে ফেরত নেওয়া টুকরো আবার ব্যবহারযোগ্য করা। অর্থাৎ malloc হলো heap-এর ভেতরের একজন ছোট ব্যবস্থাপক।

মূল ধারণা — free list

সবচেয়ে সাধারণ পদ্ধতি: খালি টুকরোগুলোর একটা linked list রাখা। প্রতিটা টুকরোর শুরুতে একটা ছোট header — কত বড়, আর free কিনা।

// প্রতিটা memory ব্লকের header
typedef struct block {
    size_t size;           // এই ব্লক কত বড়
    int free;              // খালি না ব্যবহৃত (1 = free)
    struct block *next;    // পরের ব্লক
} block_t;

ধাপ ১ — একটা সরল allocator

#include <unistd.h>   // sbrk
#include <stddef.h>

static block_t *head = NULL;   // free list-এর শুরু

void *my_malloc(size_t size) {
    // ১. free list-এ যথেষ্ট বড় একটা খালি ব্লক খোঁজো (first-fit)
    block_t *cur = head;
    while (cur) {
        if (cur->free && cur->size >= size) {
            cur->free = 0;
            return (cur + 1);   // header-এর পরের অংশ ফেরত দাও
        }
        cur = cur->next;
    }
    // ২. না পেলে OS থেকে নতুন জায়গা নাও (sbrk heap বাড়ায়)
    block_t *blk = sbrk(sizeof(block_t) + size);
    blk->size = size;
    blk->free = 0;
    blk->next = head;
    head = blk;
    return (blk + 1);
}

void my_free(void *ptr) {
    if (!ptr) return;
    block_t *blk = (block_t *)ptr - 1;  // header-এ ফিরে যাও
    blk->free = 1;                       // শুধু "খালি" চিহ্নিত করো
}
🛠 চালান ও যাচাই করুন উপরের কোড একটা ফাইলে রেখে main()-এ কয়েকবার my_malloc/my_free ডাকুন, ফেরত পাওয়া pointer প্রিন্ট করুন। লক্ষ্য করুন — একটা free করার পর আবার সমান আকার চাইলে একই ঠিকানা ফিরে আসে (free list পুনঃব্যবহার করছে)।

ধাপ ২ — যে সমস্যাগুলো সমাধান করতে হবে

⚠️ Internal ও External Fragmentation Internal: ১০ byte চাইলেন, কিন্তু একটা ১০০ byte ব্লক দিলাম — ৯০ byte নষ্ট (ব্লকের ভেতরে)। সমাধান: বড় ব্লক পেলে ভাগ করা (splitting) — ১০ byte দিয়ে বাকি ৯০ byte নতুন free ব্লক বানানো।
External: অনেকগুলো ছোট free ব্লক পাশাপাশি, কিন্তু একটাও যথেষ্ট বড় নয়। সমাধান: পাশাপাশি free ব্লকগুলো জোড়া লাগানো (coalescing) — free-র সময় পরের ব্লকও free হলে দুটো মিলিয়ে একটা বড় করা।

চ্যালেঞ্জ — নিজে যোগ করুন

🛠 ধাপে ধাপে উন্নত করুন
  1. Splitting: চাহিদার চেয়ে অনেক বড় ব্লক পেলে ভাগ করুন, বাকিটা free রাখুন
  2. Coalescing: free-তে পাশের free ব্লকের সাথে জোড়া লাগান
  3. Alignment: ফেরত ঠিকানা ৮ বা ১৬ byte-এ align করুন (অনেক CPU-তে দরকার)
  4. নীতি তুলনা: first-fit, best-fit, worst-fit — কোনটা কম fragmentation দেয় পরীক্ষা করুন
  5. calloc ও realloc: এই দুটোও implement করুন
🔬 গভীরে — এই প্রজেক্ট কেন এত শিক্ষণীয় নিজে malloc লিখলে হঠাৎ অনেক কিছু পরিষ্কার হয়ে যায়: কেন free করা pointer আবার ব্যবহার করা বিপজ্জনক (use-after-free — ব্লকটা এখন অন্য কাউকে দেওয়া হয়ে থাকতে পারে), কেন free-র পর pointer NULL করা ভালো, কেন buffer overflow ভয়ংকর (পরের ব্লকের header নষ্ট হয়ে পুরো free list ভেঙে যেতে পারে), আর কেন memory leak হয় (free না করলে ব্লক চিরকাল "ব্যবহৃত" থেকে যায়)। এগুলো তত্ত্বে পড়া আর নিজে হাতে দেখা — আকাশ-পাতাল পার্থক্য।
🛠 তুলনা করুন আসলটার সাথে valgrind ./your_program চালিয়ে দেখুন আপনার allocator-এ leak আছে কিনা। আর আসল malloc কীভাবে আচরণ করে দেখতে একটা প্রোগ্রামে অনেকবার malloc/free করে strace দিয়ে দেখুন কখন brk বা mmap system call হয় — বুঝবেন glibc-এর malloc কখন OS থেকে নতুন memory নেয়, আর কখন নিজের কাছে থাকা free ব্লক পুনঃব্যবহার করে।
🎓 মডিউল ৩ শেষ! আপনি এখন জানেন কেন virtual memory দরকার, address translation কীভাবে হয়, paging ও page table কীভাবে কাজ করে, TLB কেন performance-এর জন্য গুরুত্বপূর্ণ, multi-level table কীভাবে memory বাঁচায়, page fault ও swap কীভাবে RAM-এর সীমা ছাড়ায়, page replacement-এর নীতি — আর নিজে একটা malloc লিখে heap-এর ভেতরটা দেখেছেন।

এখানেই Virtualization স্তম্ভ সম্পূর্ণ। পরের ধাপে মডিউল ৪ (Concurrency) — একসাথে অনেক thread চললে জিনিস কীভাবে ভাঙে, race condition, lock, deadlock, আর producer-consumer ও dining philosophers সমাধান।
