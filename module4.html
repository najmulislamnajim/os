Concurrency

একসাথে অনেক thread চললে গতি বাড়ে — কিন্তু জিনিস ভয়ংকরভাবে ভাঙতেও পারে। এই মডিউলে দেখবো কেন counter++-ও বিপজ্জনক হতে পারে, কীভাবে lock দিয়ে বাঁচানো যায়, আর deadlock কী। OS-এর সবচেয়ে কঠিন কিন্তু বাস্তবিক অংশ।

০০

শুরুর কথা

orientation

মডিউল ২-তে thread-এর সাথে পরিচয় হয়েছে — একই process-এর ভেতরে অনেক সুতো, যারা memory ভাগ করে। সেই "memory ভাগ করা"-ই thread-এর শক্তি, আবার তার সবচেয়ে বড় বিপদ। এই মডিউল পুরোটাই সেই বিপদ ও তার সমাধান নিয়ে।

🧭 কেন এই মডিউল আলাদাভাবে গুরুত্বপূর্ণ রোডম্যাপে বলেছিলাম — এটা বাস্তব চাকরিতে সবচেয়ে বেশি কাজে লাগে। যেকোনো multithreaded ব্যাকএন্ড, database, ওয়েব সার্ভার, এমনকি আধুনিক ফ্রন্টএন্ড — সবখানে concurrency। আর concurrency-র বাগ সবচেয়ে কুখ্যাত, কারণ সেগুলো অনিয়মিত — কখনো ধরা পড়ে, কখনো না। তাই ধারণাগুলো শক্ত করে বুঝুন।
🛠 পরিবেশ — pthread এই মডিউলের কোড POSIX threads (pthread) ব্যবহার করে, যা Linux-এ বিল্ট-ইন। compile করার সময় -pthread ফ্ল্যাগ লাগবে: gcc prog.c -o prog -pthread। Mac-এও চলবে। প্রতিটা উদাহরণ নিজে চালিয়ে দেখুন — বিশেষত race condition-এরগুলো কয়েকবার চালালে ভিন্ন ফল দেখবেন।
০১

Race Condition

race-condition

শুরু করি একটা আপাত-নিরীহ কোড দিয়ে, যা ভয়ংকরভাবে ভুল ফল দেয়। দুটো thread একটা সাধারণ counter বাড়াচ্ছে — কী সমস্যা হতে পারে?

// দুটো thread, প্রত্যেকে counter ১০ লক্ষ বার বাড়ায়
#include <pthread.h>
#include <stdio.h>

int counter = 0;   // দুই thread শেয়ার করে

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        counter++;      // দেখতে সরল, কিন্তু বিপজ্জনক!
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);   // আশা করি 2000000?
    return 0;
}
⚠️ ফলাফল আপনাকে অবাক করবে আশা করেছিলেন 2000000। কিন্তু চালালে পাবেন এলোমেলো সংখ্যা — 1487213, 1892043, প্রতিবার আলাদা! কিছু বৃদ্ধি "হারিয়ে" যাচ্ছে। কেন? উত্তরটাই concurrency-র মূল সমস্যা।

কেন — counter++ আসলে তিনটা ধাপ

counter++ একটা অবিভাজ্য কাজ মনে হলেও, CPU-র জন্য এটা তিনটা আলাদা instruction:

Thread A পড়ল ৫, এর মাঝে (context switch) Thread B-ও পড়ল ৫। দুজনেই ৬ বানিয়ে লিখল। ফল — দুবার বাড়িয়েও counter ৫ থেকে মাত্র ৬ হলো, ৭ নয়। একটা বৃদ্ধি হারিয়ে গেল।

💡 সংজ্ঞা — Race Condition যখন একাধিক thread একই শেয়ার্ড ডেটা একসাথে অ্যাক্সেস করে, আর ফলাফল নির্ভর করে কে আগে চলল তার উপর (timing) — সেটাই race condition। "Race" কারণ thread-রা যেন একটা দৌড়ে, আর কে জিতবে তা অনিশ্চিত। এই অনিশ্চয়তাই এটাকে এত কুখ্যাত করে — একই কোড কখনো ঠিক চলে, কখনো ভুল।
🛠 নিজে দেখুন উপরের কোড race.c নামে সেভ করে gcc race.c -o race -pthread দিয়ে compile করুন। তারপর কয়েকবার ./race চালান — প্রতিবার ভিন্ন সংখ্যা, আর কখনোই ঠিক ২০ লক্ষ নয়। এই অনিশ্চিত আচরণ নিজ চোখে দেখাটাই এই মডিউল বোঝার প্রথম ধাপ।
🧠 যাচাই করুন
counter++ কেন atomic নয়?

এটা আসলে তিনটা CPU instruction — পড়া, যোগ, লেখা। এই তিনটার মাঝে context switch হতে পারে, তখন অন্য thread পুরনো মান দেখে ভুল হিসাব করে।

Race condition-এর ফল প্রতিবার আলাদা কেন?

কারণ ফলাফল নির্ভর করে thread-দের সঠিক timing-এর উপর — কে কখন context switch হলো। এটা scheduler ঠিক করে, যা অনির্দিষ্ট, তাই প্রতিবার ভিন্ন।

০২

Critical Section

critical-section

সমস্যা বুঝলাম। সমাধানের আগে একটা জরুরি ধারণা — critical section। এটা কোডের সেই অংশ যেখানে শেয়ার্ড ডেটা ছোঁয়া হয়, আর যেখানে একসাথে একাধিক thread থাকলে বিপদ।

🚻 উপমা — একটা টয়লেট, একটা চাবি একটা পাবলিক টয়লেট (critical section) — একসাথে একজনই ঢুকতে পারে। বাইরে একটা চাবি (lock)। যে ঢোকে সে চাবি নেয়, ভেতরে থাকে, বেরিয়ে চাবি ফেরত দেয়। বাকিরা বাইরে অপেক্ষা করে। এভাবে নিশ্চিত হয় একসময়ে একজনই ভেতরে। শেয়ার্ড ডেটাও তাই — একসময়ে একটা thread-ই ছুঁতে পারবে।

একটা সঠিক সমাধানের তিনটা শর্ত

শর্তমানে
Mutual Exclusionএকসময়ে একটা thread-ই critical section-এ থাকবে
Progressকেউ ভেতরে না থাকলে, ঢুকতে চাওয়া কেউ অনির্দিষ্টকাল আটকাবে না
Bounded waitingকেউ চিরকাল অপেক্ষায় থাকবে না (starvation নেই)
💡 মূল লক্ষ্য — mutual exclusion Race condition দূর করার মূল কৌশল: critical section-কে এমনভাবে রক্ষা করা যাতে একসময়ে একটা thread-ই সেখানে ঢুকতে পারে। বাকিদের অপেক্ষা করতে হবে। কীভাবে এই "একজনই ঢুকবে" নিশ্চিত করা যায় — সেটাই পরের অধ্যায়ের lock।
🧠 যাচাই করুন
Critical section কী?

কোডের যে অংশে শেয়ার্ড ডেটা অ্যাক্সেস করা হয়, আর যেখানে একসাথে একাধিক thread থাকলে race condition হতে পারে। এই অংশটুকু রক্ষা করতে হয়।

০৩

Lock ও Mutex

locks-and-mutexes

Lock (বা mutex — MUTual EXclusion) হলো সেই "চাবি"। একটা thread lock নেয়, critical section সারে, lock ছাড়ে। lock ধরা থাকলে অন্যরা অপেক্ষা করে।

আগের সমস্যা mutex দিয়ে সমাধান

#include <pthread.h>

int counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;   // একটা lock

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);      // চাবি নাও (দরজা বন্ধ)
        counter++;                       // critical section — এখন নিরাপদ
        pthread_mutex_unlock(&lock);    // চাবি ফেরত দাও
    }
    return NULL;
}
// এখন ফল সবসময় ঠিক 2000000!
🛠 নিজে যাচাই করুন আগের race.c-তে এই তিনটা লাইন (lock ঘোষণা, lock/unlock) যোগ করে চালান। এখন যতবারই চালান, সবসময় ঠিক ২০ লক্ষ। lock নিশ্চিত করেছে একসময়ে একটা thread-ই counter++ করছে — race condition শেষ।

Lock কীভাবে কাজ করে — atomic instruction

কিন্তু দাঁড়ান — lock নিজেই তো শেয়ার্ড ডেটা! "lock খালি আছে কিনা দেখা" আর "lock নেওয়া"-র মাঝেও তো race হতে পারে। এই মুরগি-ডিম সমস্যা সমাধান করে হার্ডওয়্যার।

🔬 গভীরে — test-and-set আধুনিক CPU-তে বিশেষ atomic instruction আছে (যেমন test-and-set, compare-and-swap) — যা একটা অবিভাজ্য ধাপে একই সাথে একটা মান পড়ে এবং নতুন মান লেখে, মাঝখানে কোনো interrupt ঢুকতে পারে না। lock এই instruction-এর উপর তৈরি: "যদি lock খালি থাকে তবে একই অবিভাজ্য ধাপে সেটা দখল করো"। হার্ডওয়্যারের এই atomic গ্যারান্টিই পুরো concurrency নিয়ন্ত্রণের ভিত্তি — সফটওয়্যার একা এটা নিশ্চিত করতে পারে না।

Spinlock বনাম Blocking lock

SpinlockBlocking (mutex)
অপেক্ষার সময়বারবার চেক করতে থাকে (ব্যস্ত থাকে)ঘুমিয়ে পড়ে, OS পরে জাগায়
ভালো যখনঅপেক্ষা খুব সংক্ষিপ্তঅপেক্ষা দীর্ঘ হতে পারে
খরচCPU নষ্ট করে (spin)context switch-এর খরচ
⚠️ Lock-এর দাম আছে Lock নিরাপত্তা দেয়, কিন্তু বিনামূল্যে নয়। (১) Performance: lock-এর জন্য অপেক্ষা মানে thread বসে থাকা — সমান্তরালতা কমে। (২) যত বেশি অংশ lock করবেন, তত কম সমান্তরাল। তাই critical section যতটা সম্ভব ছোট রাখুন — শুধু যেটুকু আসলেই শেয়ার্ড ডেটা ছোঁয়, ততটুকু। (৩) ভুল lock ব্যবহার deadlock ডেকে আনে (অধ্যায় ৬)।
🧠 যাচাই করুন
Lock নিজেই শেয়ার্ড ডেটা — তাহলে lock নেওয়ায় race হয় না কেন?

কারণ lock নেওয়া atomic hardware instruction (test-and-set/compare-and-swap) দিয়ে হয় — যা এক অবিভাজ্য ধাপে চেক ও দখল করে, মাঝখানে interrupt ঢুকতে পারে না।

Critical section ছোট রাখা কেন জরুরি?

lock ধরা থাকলে বাকি thread অপেক্ষা করে, সমান্তরালতা কমে। যত ছোট critical section, তত কম সময় lock ধরা থাকে, তত বেশি thread একসাথে এগোতে পারে।

০৪

Condition Variable

condition-variables

Lock একটা সমস্যা সমাধান করে (mutual exclusion), কিন্তু আরেকটা দরকার — সমন্বয়। কখনো একটা thread-কে অপেক্ষা করতে হয় "একটা শর্ত সত্য হওয়া পর্যন্ত"। যেমন — বাফার খালি হলে তবেই লিখব। এই অপেক্ষা করায় condition variable।

🔔 উপমা — রেস্তোরাঁর অর্ডার বেল রাঁধুনি (consumer) খাবার তৈরির অপেক্ষায়। সে বারবার রান্নাঘরে উঁকি দিতে পারে (busy waiting — CPU নষ্ট), অথবা বিশ্রাম নিতে পারে আর ওয়েটার একটা বেল বাজিয়ে ডাকবে "অর্ডার এসেছে!" (condition variable)। দ্বিতীয়টা দক্ষ — thread ঘুমায়, শর্ত সত্য হলে অন্য thread তাকে "signal" দিয়ে জাগায়।

তিনটা অপারেশন

অপারেশনকাজ
wait()lock ছেড়ে ঘুমিয়ে পড়ো, signal পেলে জাগো ও আবার lock নাও
signal()একটা অপেক্ষমাণ thread-কে জাগাও
broadcast()সব অপেক্ষমাণ thread-কে জাগাও
// consumer: বাফারে জিনিস আসা পর্যন্ত অপেক্ষা
pthread_mutex_lock(&lock);
while (count == 0) {                 // শর্ত: বাফার খালি?
    pthread_cond_wait(&not_empty, &lock);  // ঘুমাও (lock ছেড়ে দিয়ে)
}
// এখানে এলে count > 0 নিশ্চিত — জিনিস নাও
item = buffer[--count];
pthread_mutex_unlock(&lock);

// producer: জিনিস রেখে consumer-কে জাগাও
pthread_mutex_lock(&lock);
buffer[count++] = item;
pthread_cond_signal(&not_empty);     // "বাফারে জিনিস আছে!"
pthread_mutex_unlock(&lock);
⚠️ সবসময় while, কখনো if নয় লক্ষ্য করুন — শর্ত চেক করা হয়েছে while দিয়ে, if দিয়ে নয়। কারণ spurious wakeup (কারণ ছাড়াই জেগে ওঠা) হতে পারে, বা signal পাওয়ার পরও অন্য thread আগে ঢুকে শর্ত আবার মিথ্যা করে দিতে পারে। তাই জাগার পর আবার শর্ত যাচাই করা জরুরি। if ব্যবহার করলে সূক্ষ্ম, কঠিন-ধরা বাগ তৈরি হয় — এটা concurrency-র একটা ক্লাসিক ভুল।
🧠 যাচাই করুন
Condition variable আর lock-এর কাজ কীভাবে আলাদা?

Lock দেয় mutual exclusion (একসাথে একজন)। Condition variable দেয় সমন্বয় — একটা thread শর্তের জন্য অপেক্ষা করে ঘুমায়, অন্যটা শর্ত সত্য হলে তাকে জাগায়। দুটো একসাথে ব্যবহার হয়।

শর্ত চেক করতে while কেন, if নয়?

Spurious wakeup বা signal-এর পর অন্য thread শর্ত আবার মিথ্যা করে দিতে পারে। তাই জাগার পর আবার যাচাই করা দরকার — while সেটা নিশ্চিত করে।

০৫

Semaphore

semaphores

Semaphore হলো একটা আরও সাধারণ সমন্বয় টুল — মূলত একটা গণনাকারী (counter) যা নিরাপদে বাড়ানো-কমানো যায়। এটা দিয়ে lock ও condition variable দুটোরই কাজ করা যায়।

🅿️ উপমা — পার্কিং লটের খালি জায়গার বোর্ড একটা পার্কিং লটের গেটে ডিজিটাল বোর্ড — "খালি: ১৫"। গাড়ি ঢুকলে সংখ্যা কমে (wait), বেরোলে বাড়ে (signal)। বোর্ড ০ দেখালে গেট বন্ধ — নতুন গাড়ি অপেক্ষা করে যতক্ষণ না কেউ বেরোয়। semaphore ঠিক এই গণনাকারী — কতগুলো "সম্পদ" খালি আছে তা রাখে।

দুটো অপারেশন

অপারেশনযাকে বলেকাজ
wait()P / down / acquireমান ১ কমাও; ০ হলে অপেক্ষা করো
signal()V / up / releaseমান ১ বাড়াও; কেউ অপেক্ষায় থাকলে জাগাও

দুই ধরনের ব্যবহার

Binary semaphore (মান ০ বা ১): কার্যত একটা lock-এর মতো — mutual exclusion।

Counting semaphore (যেকোনো মান): সীমিত সংখ্যক সম্পদ নিয়ন্ত্রণ — যেমন "একসাথে সর্বোচ্চ ৫টা thread এই কাজ করতে পারবে"।

#include <semaphore.h>

sem_t sem;
sem_init(&sem, 0, 3);   // শুরুতে মান ৩ (একসাথে ৩ জন ঢুকতে পারবে)

void *worker(void *arg) {
    sem_wait(&sem);      // একটা "স্লট" নাও (মান কমল)
    // ... সীমিত সম্পদ ব্যবহার করো ...
    sem_post(&sem);      // স্লট ফেরত দাও (মান বাড়ল)
    return NULL;
}
💡 কখন কোনটা? Lock/mutex: সরল mutual exclusion, একজন মালিক। Condition variable: একটা নির্দিষ্ট শর্তের জন্য অপেক্ষা। Semaphore: গণনা করা সম্পদ, বা producer-consumer-এর মতো সমস্যা যেখানে "কতগুলো আছে" গোনা দরকার। বাস্তবে তিনটাই দরকার হয়; কোন সমস্যায় কোনটা সবচেয়ে পরিষ্কার সমাধান দেয়, সেটাই বাছাইয়ের মাপকাঠি।
🧠 যাচাই করুন
Binary আর counting semaphore-এর পার্থক্য?

Binary-র মান শুধু ০/১ — কার্যত lock। Counting-এর মান যেকোনো — সীমিত সংখ্যক সম্পদ নিয়ন্ত্রণে (যেমন সর্বোচ্চ N thread একসাথে)।

Semaphore-এর মান ৫ থেকে শুরু হলে মানে কী?

৫টা "সম্পদ" বা স্লট খালি — একসাথে ৫টা thread wait করে ঢুকতে পারবে। ষষ্ঠটি অপেক্ষা করবে যতক্ষণ না কেউ signal দেয়।

০৬

Deadlock

deadlock

Lock সমস্যা সমাধান করে, কিন্তু ভুলভাবে ব্যবহার করলে নতুন — আর ভয়ংকর — সমস্যা তৈরি করে: deadlock। দুটো thread একে অপরের জন্য চিরকাল অপেক্ষা করে, কেউ এগোয় না।

🚗 উপমা — সরু গলিতে মুখোমুখি দুই গাড়ি একটা সরু গলিতে দুটো গাড়ি মুখোমুখি এসে থেমে গেছে। A এগোতে পারবে যদি B পিছিয়ে যায়; B এগোতে পারবে যদি A পিছিয়ে যায়। কেউ পিছবে না — দুজনেই চিরকাল আটকে। এটাই deadlock — প্রত্যেকে অন্যের ছেড়ে দেওয়া কিছুর জন্য অপেক্ষা করছে।

একটা ক্লাসিক deadlock

// Thread 1              |  Thread 2
lock(A);              // |  lock(B);
lock(B);  // ⟵ আটকে   |  lock(A);  // ⟵ আটকে
// Thread 1-এর হাতে A, চায় B  |  Thread 2-এর হাতে B, চায় A
// দুজনেই চিরকাল অপেক্ষা করবে — DEADLOCK

Deadlock-এর চারটা শর্ত (Coffman conditions)

Deadlock হতে চারটাই একসাথে লাগে। যেকোনো একটা ভাঙলে deadlock অসম্ভব:

শর্তমানে
Mutual exclusionসম্পদ একসাথে একজনই ব্যবহার করতে পারে
Hold and waitএকটা ধরে রেখে আরেকটার জন্য অপেক্ষা
No preemptionজোর করে কারো lock কেড়ে নেওয়া যায় না
Circular waitএকটা বৃত্তাকার শৃঙ্খল — A চায় B, B চায় A
💡 সবচেয়ে সহজ প্রতিরোধ — lock ordering Circular wait ভাঙাই সবচেয়ে সহজ ব্যবহারিক উপায়। নিয়ম: সব thread সবসময় একই ক্রমে lock নেবে (যেমন সবসময় আগে A, তারপর B — কখনো উল্টো নয়)। তাহলে বৃত্ত তৈরি হতে পারে না, deadlock অসম্ভব। উপরের উদাহরণে Thread 2-ও যদি আগে A তারপর B নিত, deadlock হতো না। এই সরল নিয়মটাই বাস্তব কোডে সবচেয়ে বেশি ব্যবহৃত।
🔬 গভীরে — প্রতিরোধ, এড়ানো, সনাক্তকরণ Prevention: চার শর্তের একটা স্থায়ীভাবে ভাঙা (যেমন lock ordering)। Avoidance: চলার সময় হিসাব করে এমন অবস্থা এড়ানো যেখান থেকে deadlock সম্ভব (Banker's algorithm — কিন্তু ব্যবহারিক নয়, সব সম্পদের চাহিদা আগে জানতে হয়)। Detection & recovery: deadlock হতে দাও, তারপর ধরো (সম্পদ-গ্রাফে চক্র খুঁজে) আর একটা thread মেরে/পিছিয়ে ভাঙো — database এই পদ্ধতি ব্যবহার করে (deadlock ধরে একটা transaction rollback করে)। বাস্তবে বেশিরভাগ সাধারণ প্রোগ্রাম prevention (lock ordering) ব্যবহার করে, কারণ সেটা সহজ ও নির্ভরযোগ্য।
⚠️ Deadlock বনাম Livelock বনাম Starvation Deadlock: সবাই আটকে, কেউ নড়ে না। Livelock: thread-রা নড়ছে (অবস্থা বদলাচ্ছে) কিন্তু কেউ এগোচ্ছে না — যেমন দুজন করিডোরে মুখোমুখি, দুজনেই একই দিকে সরে বারবার আবার মুখোমুখি। Starvation: কিছু thread এগোচ্ছে, কিন্তু একটা নির্দিষ্ট thread কখনো সুযোগ পাচ্ছে না (সবসময় অন্যরা আগে)। তিনটাই "এগোনো"-র সমস্যা, কিন্তু আলাদা।
🧠 যাচাই করুন
Lock ordering কীভাবে deadlock ঠেকায়?

সব thread একই ক্রমে lock নিলে circular wait অসম্ভব হয়ে যায় — বৃত্ত তৈরি হতে পারে না। চার শর্তের একটা ভাঙায় deadlock হয় না।

Deadlock আর starvation কীভাবে আলাদা?

Deadlock-এ কেউই এগোয় না (সবাই পরস্পরের জন্য আটকে)। Starvation-এ সিস্টেম এগোচ্ছে, কিন্তু একটা নির্দিষ্ট thread বারবার উপেক্ষিত হয়ে কখনো সুযোগ পায় না।

০৭

ক্লাসিক Concurrency সমস্যা

classic-problems

কয়েকটা ক্লাসিক সমস্যা আছে যা concurrency-র মূল চ্যালেঞ্জগুলো ধরে রাখে। এগুলো শুধু একাডেমিক নয় — বাস্তব সিস্টেমের প্যাটার্ন, আর ইন্টারভিউতেও আসে।

১. Producer-Consumer (Bounded Buffer)

এক বা একাধিক producer ডেটা তৈরি করে একটা সীমিত বাফারে রাখে; consumer সেখান থেকে নিয়ে ব্যবহার করে। সমস্যা: বাফার ভরা থাকলে producer অপেক্ষা করবে, খালি থাকলে consumer অপেক্ষা করবে — আর দুজনের একসাথে বাফার ছোঁয়ায় race হবে না।

🍞 উপমা — বেকারি ও তাক বেকার (producer) রুটি বানিয়ে তাকে (বাফার) রাখে। ক্রেতা (consumer) তাক থেকে নেয়। তাক ভরে গেলে বেকার থামে; তাক খালি হলে ক্রেতা অপেক্ষা করে। আর দুজন একসাথে একই জায়গায় হাত দিলে গোলমাল — তাই সমন্বয় দরকার।
🔧 সমাধানের কাঠামো — তিনটা টুল একসাথে একটা mutex — বাফার ছোঁয়ার সময় mutual exclusion।
দুটো semaphore — empty (কতগুলো খালি স্লট, শুরুতে = বাফার সাইজ) আর full (কতগুলো ভরা স্লট, শুরুতে = ০)।
Producer: wait(empty) → lock → রাখো → unlock → signal(full)।
Consumer: wait(full) → lock → নাও → unlock → signal(empty)।
এই প্যাটার্নটা মুখস্থ রাখার মতো — বহু বাস্তব সমস্যার ভিত্তি (message queue, thread pool, pipeline)।

২. Readers-Writers

একটা শেয়ার্ড ডেটা — অনেকে একসাথে পড়তে পারে (কোনো সমস্যা নেই), কিন্তু কেউ লিখলে তাকে একা থাকতে হবে (পড়া ও লেখা একসাথে হলে বিপদ)। চ্যালেঞ্জ: যতটা সম্ভব বেশি reader-কে একসাথে চলতে দেওয়া, অথচ writer-কে একচেটিয়া অ্যাক্সেস দেওয়া — আর কেউ যেন starve না করে।

💡 বাস্তব প্রয়োগ এটা সরাসরি database ও cache-এ ব্যবহৃত হয় — একটা read-write lock (rwlock)। বেশিরভাগ কাজ যখন পড়া (যেমন একটা কনফিগ যা কদাচিৎ বদলায়), তখন সব reader-কে একসাথে চলতে দিয়ে অনেক বেশি সমান্তরালতা পাওয়া যায়, শুধু বিরল লেখার সময় একচেটিয়া lock নেওয়া হয়।

৩. Dining Philosophers

পাঁচজন দার্শনিক একটা গোল টেবিলে। প্রতি দুজনের মাঝে একটা করে কাঁটা (মোট ৫টা)। খেতে হলে দুই পাশের দুটো কাঁটা লাগে। সবাই যদি একসাথে বাঁ দিকের কাঁটা তুলে ডানেরটার জন্য অপেক্ষা করে — deadlock! কেউ কখনো খেতে পারবে না।

💡 সমাধানের কয়েকটা কৌশল Lock ordering: কাঁটাগুলো নম্বর দাও, সবাই আগে ছোট নম্বরের কাঁটা তুলবে। তাহলে অন্তত একজন দুটো পাবে (circular wait ভাঙে)। Asymmetry: একজন দার্শনিক উল্টো ক্রমে তুলবে। Limiting: একসাথে সর্বোচ্চ ৪ জনকে বসতে দাও (একটা counting semaphore) — তাহলে অন্তত একজন দুটো কাঁটা পাবেই। এই সমস্যাটাই deadlock-এর চার শর্ত ও তাদের ভাঙার উপায় হাতে-কলমে শেখায়।
🧠 যাচাই করুন
Producer-consumer-এ দুটো semaphore কেন লাগে?

একটা (empty) গোনে কতগুলো খালি স্লট — producer-কে থামায় বাফার ভরা হলে। আরেকটা (full) গোনে কতগুলো ভরা — consumer-কে থামায় বাফার খালি হলে। সাথে mutex বাফার রক্ষা করে।

Dining philosophers-এ deadlock কীভাবে ঠেকানো যায়?

কয়েকভাবে — কাঁটায় ক্রম আরোপ (lock ordering), একজনকে উল্টো ক্রমে তোলানো, বা একসাথে সর্বোচ্চ ৪ জনকে বসতে দেওয়া। সবগুলোই circular wait ভাঙে।

প্রজেক্ট — Concurrency হাতে-কলমে

projects

এই মডিউলের ধারণাগুলো শুধু পড়ে বোঝা যায় না — কোডে দেখতে হয়, ভাঙতে হয়, ঠিক করতে হয়। তিনটা প্রজেক্ট, সহজ থেকে কঠিন।

🛠 প্রজেক্ট ১ — Race দেখা ও সারানো অধ্যায় ১-এর race.c দিয়ে শুরু করুন।
  1. lock ছাড়া চালিয়ে কয়েকবার ভুল ফল দেখুন (প্রতিবার ভিন্ন)
  2. mutex যোগ করে ঠিক করুন — এখন সবসময় ২০ লক্ষ
  3. পরীক্ষা করুন: lock শুধু counter++-এর চারপাশে বনাম পুরো লুপের চারপাশে — গতির পার্থক্য মাপুন (time ./race)। শিখবেন কেন critical section ছোট রাখা জরুরি
🛠 প্রজেক্ট ২ — Bounded Buffer (মূল প্রজেক্ট) একটা producer-consumer সিস্টেম বানান pthread দিয়ে:
  1. একটা নির্দিষ্ট আকারের বাফার (যেমন ১০টা স্লট, একটা array)
  2. N producer thread — এলোমেলো সংখ্যা তৈরি করে বাফারে রাখে
  3. M consumer thread — বাফার থেকে নিয়ে যোগফল হিসাব করে
  4. একটা mutex + দুটো semaphore (empty, full) দিয়ে সমন্বয়
  5. যাচাই: মোট উৎপাদিত = মোট ব্যবহৃত? (নাহলে কোথাও race)
এটাই এই মডিউলের কেন্দ্রীয় প্রজেক্ট — thread, mutex, semaphore, condition সব একসাথে।
🛠 প্রজেক্ট ৩ — Dining Philosophers (চ্যালেঞ্জ) পাঁচজন দার্শনিককে thread হিসেবে চালান, কাঁটাগুলোকে mutex হিসেবে।
  1. প্রথমে ইচ্ছাকৃতভাবে সবাইকে আগে বাঁ কাঁটা তোলান — deadlock দেখুন (প্রোগ্রাম আটকে যাবে)
  2. তারপর lock ordering দিয়ে ঠিক করুন (কাঁটায় নম্বর, ছোট আগে)
  3. যাচাই করুন সবাই খেতে পারছে, কেউ starve করছে না
Deadlock নিজে তৈরি করে তারপর সারানোটাই সবচেয়ে ভালো শিক্ষা।
🔬 debugging টুল Concurrency বাগ ধরা কঠিন, কিন্তু টুল আছে। Helgrind (valgrind-এর অংশ): valgrind --tool=helgrind ./prog — race condition ও lock সমস্যা ধরে। ThreadSanitizer: gcc -fsanitize=thread দিয়ে compile করলে চলার সময় race ধরিয়ে দেয়। এগুলো ছাড়া concurrency বাগ খোঁজা খড়ের গাদায় সুঁচ — টুল দুটো শিখে রাখুন, বাস্তব কাজে অমূল্য।
🎓 মডিউল ৪ শেষ! আপনি এখন জানেন race condition কেন হয়, critical section কী, lock/mutex কীভাবে রক্ষা করে, condition variable ও semaphore দিয়ে thread সমন্বয়, deadlock-এর চার শর্ত ও তা ভাঙার উপায়, আর producer-consumer/dining philosophers-এর মতো ক্লাসিক সমস্যা। এটাই বাস্তব চাকরিতে সবচেয়ে বেশি কাজে লাগবে।

Concurrency স্তম্ভ শেষ। পরের ধাপে মডিউল ৫ (Storage ও File System) — তৃতীয় ও শেষ স্তম্ভ Persistence। inode, journaling, disk scheduling, আর নিজে একটা ছোট file system বানানো।
