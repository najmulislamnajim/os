Storage ও
File System

RAM-এর সব মুছে যায় বিদ্যুৎ গেলে। তাহলে আপনার ফাইল, ছবি, কোড টিকে থাকে কীভাবে? এই মডিউলে দেখবো disk কীভাবে কাজ করে, file system কীভাবে বিশৃঙ্খল block-কে গোছানো ফাইলে রূপ দেয়, আর crash-এও ডেটা কীভাবে বাঁচে।

০০

শুরুর কথা

orientation

এতক্ষণ Virtualization (CPU, memory) আর Concurrency দেখেছি। এবার শেষ স্তম্ভ — Persistence। মূল পার্থক্য: RAM volatile (বিদ্যুৎ গেলে মুছে যায়), কিন্তু disk persistent (থেকে যায়)। এই স্থায়িত্ব সামলানোই file system-এর কাজ।

🧭 এই মডিউলের কেন্দ্রীয় প্রশ্ন Disk আসলে শুধু একটা বিশাল সংখ্যক অভিন্ন block (যেমন ৫১২ byte বা ৪ KB করে)। এই সমতল, নম্বরযুক্ত block-এর সমুদ্র থেকে কীভাবে "ফোল্ডার", "ফাইল", "নাম", "সাইজ" — এই গোছানো ধারণাগুলো তৈরি হয়? সেটাই file system-এর জাদু, আর এই মডিউলের বিষয়।
🛠 পরিবেশ আগের মতোই Linux/WSL2 + gcc। প্রজেক্টে একটা সাধারণ ফাইলকে "ভার্চুয়াল ডিস্ক" ধরে তার উপর file system বানাবেন — কোনো আসল disk বা root অ্যাক্সেস লাগবে না। চাইলে FUSE (sudo apt install libfuse-dev) দিয়ে আরও এগোতে পারবেন।
০১

Disk-এর বাস্তবতা

how-disks-work

File system বোঝার আগে বুঝতে হবে সে কীসের উপর কাজ করছে। Disk-এর একটা মৌলিক বৈশিষ্ট্য পুরো file system ডিজাইনকে আকার দেয়: disk ভয়ংকর ধীর, আর HDD-তে সেটা অসম।

HDD — ঘূর্ণায়মান থালা

ঐতিহ্যবাহী hard disk-এ ঘূর্ণায়মান চাকতি (platter) আর একটা নড়াচড়া করা হাত (head)। একটা নির্দিষ্ট জায়গার ডেটা পড়তে দুটো দেরি হয়:

দেরিকীকেন ধীর
Seek timehead-কে সঠিক track-এ সরানোযান্ত্রিক নড়াচড়া — সবচেয়ে ধীর
Rotational delayসঠিক sector ঘুরে head-এর নিচে আসাচাকতির ঘূর্ণনের অপেক্ষা
Transfer timeআসল ডেটা পড়াতুলনামূলক দ্রুত
⚠️ সংখ্যায় দেখুন — কত ধীর একটা সাধারণ HDD seek-এ প্রায় ১০ মিলিসেকেন্ড লাগে। CPU সেই ১০ ms-এ কোটি কোটি instruction চালাতে পারত! অর্থাৎ একটা random disk অ্যাক্সেস RAM অ্যাক্সেসের চেয়ে প্রায় লক্ষ গুণ ধীর। এজন্যই file system-এর মূল লক্ষ্য: যতটা সম্ভব কম ও ক্রমিক (sequential) disk অ্যাক্সেস করা।
📀 উপমা — পুরনো জুকবক্স HDD যেন একটা জুকবক্স — একটা যান্ত্রিক হাত রেকর্ড খুঁজে সুচ নামায়। এক গান থেকে আরেক গানে লাফ দিতে হাত সরাতে হয় (seek), তারপর সঠিক জায়গা ঘুরে আসার অপেক্ষা (rotation)। পাশাপাশি গান শুনলে দ্রুত, কিন্তু এলোমেলো লাফালে প্রতিবার দেরি। disk-ও তাই — sequential দ্রুত, random ধীর।

SSD — কোনো নড়াচড়া নেই

আধুনিক SSD-তে কোনো যান্ত্রিক অংশ নেই — সব ইলেকট্রনিক (flash memory)। তাই seek time প্রায় নেই, random অ্যাক্সেস অনেক দ্রুত। কিন্তু SSD-রও নিজস্ব বৈশিষ্ট্য আছে:

🔬 গভীরে — SSD কেন আলাদা SSD পড়া ও লেখা করে "page" এককে, কিন্তু মুছতে হয় বড় "block" এককে (কয়েকটা page মিলে)। আর প্রতিটা cell সীমিতবার লেখা যায় (wear)। তাই SSD-র controller wear leveling করে (লেখা সব cell-এ ছড়িয়ে দেয়) আর TRIM ব্যবহার করে (কোন block আর লাগবে না তা জানায়)। ফলে HDD-র জন্য অপ্টিমাইজ করা কিছু কৌশল (যেমন ডেটা পাশাপাশি রাখা) SSD-তে কম গুরুত্বপূর্ণ, কিন্তু "কম লেখা" এখন আরও জরুরি (cell আয়ু বাঁচাতে)।
🧠 যাচাই করুন
HDD-তে seek time কেন সবচেয়ে ধীর অংশ?

এটা যান্ত্রিক নড়াচড়া — head-কে ফিজিক্যালি সঠিক track-এ সরাতে হয়। ইলেকট্রনিক অপারেশনের চেয়ে যান্ত্রিক নড়াচড়া বহুগুণ ধীর।

File system কেন sequential অ্যাক্সেস পছন্দ করে?

Sequential-এ head একই জায়গায় থাকে বা পাশে সরে (কম seek), তাই দ্রুত। Random অ্যাক্সেসে বারবার seek লাগে, যা লক্ষ গুণ ধীর হতে পারে।

০২

File ও Directory

files-and-directories

Disk শুধু নম্বরযুক্ত block-এর সমুদ্র। File system সেই সমুদ্রের উপর দুটো মূল বিমূর্ততা (abstraction) তৈরি করে — file (byte-এর একটা নামযুক্ত সিকোয়েন্স) আর directory (ফাইলের একটা সংগ্রহ)।

🗂️ উপমা — অফিসের ফাইলিং ক্যাবিনেট Disk যেন একটা বিশাল গুদাম ভরা সংখ্যাযুক্ত বাক্স (block)। একা এই বাক্সগুলো অর্থহীন। File system একজন গ্রন্থাগারিকের মতো — সে একটা সূচি রাখে: "প্রকল্প রিপোর্ট" নামের নথিটা ১২, ৪৫, ৪৬ নম্বর বাক্সে আছে। আপনি নাম বলেন, সে বাক্সগুলো খুঁজে দেয়। directory হলো এই সূচির ফোল্ডার-কাঠামো।

File — শুধু byte, বাকিটা ব্যাখ্যা

OS-এর কাছে একটা ফাইল শুধু byte-এর একটা সিকোয়েন্স — সে জানে না ওটা ছবি না টেক্সট না ভিডিও। সেই ব্যাখ্যা করে অ্যাপ্লিকেশন (এক্সটেনশন বা ভেতরের গঠন দেখে)। OS শুধু জানে: ফাইলটা কত বড়, কোন block-এ আছে, কার অনুমতি আছে।

Directory — নাম থেকে inode-এর ম্যাপ

মজার ব্যাপার — একটা directory আসলে নিজেই একটা বিশেষ ফাইল! তার ভেতরের ডেটা হলো একটা তালিকা: প্রতিটা এন্ট্রিতে একটা নাম আর একটা inode নম্বর (ফাইলটার আসল তথ্য কোথায়, পরের অধ্যায়)।

💡 এই বিভাজন কেন গুরুত্বপূর্ণ নাম (directory-তে) আর ফাইলের আসল তথ্য (inode-এ) আলাদা রাখার একটা সুন্দর পরিণতি: একই ফাইলের একাধিক নাম থাকতে পারে (hard link) — দুটো directory এন্ট্রি একই inode নম্বরে নির্দেশ করে। ফাইল সরানো (rename) মানে শুধু directory এন্ট্রি বদলানো, আসল ডেটা এক byte-ও নড়ে না। এই মার্জিত বিভাজনই UNIX file system-এর ভিত্তি।
🔬 গভীরে — . এবং .. কী? প্রতিটা directory-তে দুটো বিশেষ এন্ট্রি স্বয়ংক্রিয়ভাবে থাকে: . (নিজের inode-এ নির্দেশ করে) আর .. (parent directory-র inode-এ)। এজন্যই cd .. কাজ করে — এটা আসলে .. এন্ট্রি দেখে parent-এ যায়। root directory (/)-এ .. নিজের দিকেই নির্দেশ করে (উপরে আর কিছু নেই)। ছোট্ট কিন্তু গভীর ডিজাইন।
🧠 যাচাই করুন
একটা directory আসলে কী?

একটা বিশেষ ফাইল, যার ডেটা হলো নাম→inode নম্বরের একটা তালিকা। এটা ফাইলের আসল বিষয়বস্তু রাখে না, শুধু "কোন নামের ফাইলের তথ্য কোন inode-এ" তা রাখে।

ফাইলের নাম আর ফাইলের তথ্য আলাদা রাখার একটা সুবিধা?

একই ফাইলের একাধিক নাম সম্ভব (hard link), আর rename করতে শুধু directory এন্ট্রি বদলালেই হয় — আসল ডেটা সরাতে হয় না।

০৩

inode — ফাইলের আসল পরিচয়

inode

Directory নাম থেকে একটা inode নম্বর দেয়। কিন্তু inode কী? এটাই একটা ফাইলের সম্পূর্ণ পরিচয়পত্র — নাম বাদে ফাইল সম্পর্কে সব তথ্য এখানে।

একটা inode-এ কী থাকে

তথ্যউদাহরণ
ফাইলের ধরনসাধারণ ফাইল / directory / link
সাইজকত byte
অনুমতিকে পড়তে/লিখতে/চালাতে পারে (rwx)
মালিকuser ও group ID
সময়তৈরি, শেষ পরিবর্তন, শেষ অ্যাক্সেস
link countকতগুলো নাম এই inode-এ নির্দেশ করছে
block pointerআসল ডেটা কোন কোন block-এ (সবচেয়ে জরুরি)
⚠️ লক্ষ্য করুন — নাম নেই! inode-এ ফাইলের নাম নেই। নাম থাকে directory-তে। এটা প্রথমে অদ্ভুত লাগে, কিন্তু এটাই hard link-কে সম্ভব করে — একটা inode-এর অনেক নাম থাকতে পারে বিভিন্ন directory-তে, আর inode শুধু গোনে কতগুলো নাম তাকে নির্দেশ করছে (link count)। শেষ নামটা মুছলে (link count = 0) তবেই আসল ডেটা মুছে যায়।

Block pointer — বড় ফাইলের চতুর সমাধান

একটা inode-এ সীমিত জায়গা, কিন্তু ফাইল বিশাল হতে পারে (GB)। সব block-এর নম্বর কীভাবে রাখবে? সমাধান — multi-level (indirect) pointer:

💡 কেন এই ডিজাইন চমৎকার বেশিরভাগ ফাইল ছোট। তাই inode-এ কয়েকটা direct pointer (সরাসরি ডেটা block-এ) — ছোট ফাইলের জন্য এতেই যথেষ্ট, দ্রুত। ফাইল বড় হলে indirect pointer ব্যবহার হয় — একটা block ভরা থাকে আরও pointer দিয়ে, যা শত শত block নির্দেশ করে। আরও বড় হলে double/triple indirect। ফলে ছোট ফাইলে কোনো overhead নেই, অথচ বিশাল ফাইলও সামলানো যায়। এটা মডিউল ৩-এর multi-level page table-এর মতোই ধারণা!
🧠 যাচাই করুন
inode-এ কী নেই যা directory-তে আছে?

ফাইলের নাম। inode-এ সাইজ, অনুমতি, block pointer সব আছে — কিন্তু নাম থাকে directory এন্ট্রিতে।

ছোট ফাইলে indirect block লাগে না কেন?

ছোট ফাইলের block সংখ্যা কম, তাই inode-এর কয়েকটা direct pointer-এই ধরে যায়। indirect block শুধু বড় ফাইলে দরকার হয় — এতে ছোট ফাইলে কোনো বাড়তি খরচ নেই।

০৪

একটা ফাইল খোঁজার পুরো যাত্রা

path-resolution

এবার সব একসাথে জোড়া লাগাই। আপনি /home/rahim/notes.txt খুললে, disk-এ ঠিক কী কী ঘটে? এই যাত্রাটা inode আর directory কীভাবে একসাথে কাজ করে তা দেখায়।

Disk-এর সাধারণ কাঠামো

একটা file system disk-কে কয়েকটা অঞ্চলে ভাগ করে:

Superblock: পুরো file system সম্পর্কে তথ্য (কত বড়, কতগুলো inode, কোথায় কী)। Bitmap: কোন inode ও data block খালি, কোনটা ব্যবহৃত। inode টেবিল: সব inode একসাথে। Data block: আসল ফাইলের বিষয়বস্তু।

/home/rahim/notes.txt খোলার ধাপ

🔍 নাম থেকে ডেটা — ধাপে ধাপে ১. root inode (/) সবসময় জানা (যেমন inode ২)। সেটা পড়ো।
২. root-এর data block পড়ো (এটা একটা directory) → home খুঁজে তার inode নম্বর পাও।
৩. home-এর inode পড়ো → তার data block পড়ো → rahim-এর inode নম্বর পাও।
৪. rahim-এর inode পড়ো → data block পড়ো → notes.txt-এর inode নম্বর পাও।
৫. notes.txt-এর inode পড়ো → এতে আছে block pointer → সেই data block পড়ো → অবশেষে আসল বিষয়বস্তু!
⚠️ কত disk অ্যাক্সেস! লক্ষ্য করুন — একটা ফাইল খুলতে path-এর প্রতিটা অংশের জন্য inode ও data block পড়তে হলো। গভীর path (/a/b/c/d/e/file) মানে অনেক disk অ্যাক্সেস। এজন্যই OS এগুলো cache করে (অধ্যায় ৭) — একবার খোঁজা path পরে দ্রুত হয়। এটাও বোঝায় কেন খুব গভীর directory কাঠামো একটু ধীর।
🧠 যাচাই করুন
Path resolution root থেকে শুরু হয় কেন?

কারণ শুধু root inode-এর অবস্থান আগে থেকে জানা (fixed)। বাকি প্রতিটা অংশ খুঁজতে তার parent directory পড়তে হয় — তাই root থেকে ধাপে ধাপে নামতে হয়।

গভীর directory path কেন একটু ধীর?

path-এর প্রতিটা অংশের জন্য একটা directory-র inode ও data block পড়তে হয়। যত গভীর, তত বেশি disk অ্যাক্সেস — যদিও cache এটা অনেকটা কমায়।

০৫

Crash ও Journaling

crash-consistency

একটা ভয়ংকর প্রশ্ন: ফাইল লেখার মাঝখানে যদি বিদ্যুৎ চলে যায়? file system অর্ধেক-লেখা, অসংগত অবস্থায় থেকে যেতে পারে। এই সমস্যা সমাধানই আধুনিক file system-এর সবচেয়ে গুরুত্বপূর্ণ কাজগুলোর একটা।

সমস্যা — একটা কাজ, অনেক ধাপ

একটা ফাইলে নতুন ডেটা যোগ করতে file system-কে কয়েকটা আলাদা জায়গায় লিখতে হয়: (১) data block-এ আসল ডেটা, (২) inode-এ নতুন সাইজ ও block pointer, (৩) bitmap-এ "এই block এখন ব্যবহৃত"। এই তিনটা লেখার মাঝখানে crash হলে?

⚠️ অসংগত অবস্থার উদাহরণ ধরুন bitmap-এ block-টা "ব্যবহৃত" চিহ্নিত হলো, কিন্তু inode-এ pointer লেখার আগেই crash। এখন ওই block "ব্যবহৃত" দেখাচ্ছে অথচ কোনো ফাইল সেটা ব্যবহার করছে না — চিরতরে হারানো জায়গা (leak)। আরও খারাপ: inode-এ pointer লেখা হলো কিন্তু bitmap আপডেট হলো না — একই block পরে অন্য ফাইলকেও দেওয়া হতে পারে, দুই ফাইল একই জায়গা ভাগ করবে, ডেটা নষ্ট!
📒 উপমা — হিসাবের খাতা ব্যাংক টাকা সরানোর আগে খাতায় লিখে রাখে "A থেকে B-তে ৫০০ যাবে" (journal)। তারপর আসল কাজ করে। মাঝপথে বিভ্রাট হলেও খাতা দেখে বোঝা যায় কাজটা সম্পূর্ণ হয়েছিল কিনা, আর দরকারে আবার করা যায়। Journaling file system ঠিক এই কৌশল ব্যবহার করে।

সমাধান — Journaling (Write-Ahead Logging)

মূল ধারণা: আসল জায়গায় লেখার আগে, একটা আলাদা "journal" অঞ্চলে লিখে রাখো "আমি কী কী করতে যাচ্ছি"। ধাপ:

🔧 Journaling-এর ধাপ ১. journal-এ লেখো: "এই block, এই inode, এই bitmap আপডেট করব" (এটা একটা transaction)।
২. journal-এ একটা "commit" চিহ্ন লেখো (transaction সম্পূর্ণ লেখা হয়েছে)।
৩. এবার আসল জায়গায় পরিবর্তনগুলো করো (checkpoint)।
৪. সফল হলে journal থেকে transaction মুছে দাও।

Crash হলে: রিবুটের পর OS journal দেখে। commit চিহ্ন থাকলে কাজটা আবার করে (redo) — সম্পূর্ণ হয়। commit না থাকলে অসম্পূর্ণ transaction বাতিল করে। কোনো অবস্থাতেই file system অসংগত থাকে না।
🔬 গভীরে — সব কি journal করতে হয়? পুরো ডেটা journal করলে সবকিছু দুবার লেখা হয় (একবার journal-এ, একবার আসল জায়গায়) — ধীর। তাই বেশিরভাগ file system (যেমন Linux-এর ext4) ডিফল্টে শুধু metadata (inode, bitmap, directory) journal করে, আসল ফাইল ডেটা নয় (ordered mode)। এতে file system-এর কাঠামো সবসময় সংগত থাকে (crash-এ file system ভাঙে না), যদিও কিছু সাম্প্রতিক ফাইল ডেটা হারাতে পারে। এটা নিরাপত্তা ও গতির একটা ব্যবহারিক সমঝোতা — সম্পূর্ণ data journaling সম্ভব কিন্তু ধীর।
🧠 যাচাই করুন
Journaling ছাড়া crash হলে file system-এর কী সমস্যা?

একাধিক ধাপের লেখার মাঝে crash হলে অসংগত অবস্থা — যেমন block "ব্যবহৃত" চিহ্নিত অথচ কোনো ফাইল ব্যবহার করছে না (leak), বা একই block দুই ফাইলকে দেওয়া (ডেটা নষ্ট)।

ext4 কেন শুধু metadata journal করে, সব ডেটা নয়?

সব ডেটা journal করলে সবকিছু দুবার লেখা হয় — ধীর। শুধু metadata journal করলে file system-এর কাঠামো সংগত থাকে, অথচ গতি ভালো থাকে। এটা একটা সমঝোতা।

০৬

Disk Scheduling

disk-scheduling

অনেকগুলো disk request একসাথে অপেক্ষা করছে (বিভিন্ন process থেকে)। HDD-তে head-এর নড়াচড়া ধীর, তাই কোন request আগে সারালে মোট head movement কম হয় — এই সিদ্ধান্তই disk scheduling।

🛗 উপমা — লিফট একটা লিফটে বিভিন্ন তলার বোতাম চাপা। লিফট কি চাপার ক্রমে যাবে (এলোমেলো, অদক্ষ)? না — এক দিকে যেতে যেতে পথের সব তলা সারে, তারপর উল্টো দিকে ফেরে। disk-এর SCAN অ্যালগরিদম ঠিক এই "লিফট" পদ্ধতি — head এক দিকে যেতে যেতে পথের সব request সারে।

মূল অ্যালগরিদম

অ্যালগরিদমধারণাসমস্যা
FCFSআসার ক্রমেhead বেশি নড়ে, অদক্ষ
SSTFসবচেয়ে কাছের request আগেদূরের request starve করতে পারে
SCAN (লিফট)এক দিকে গিয়ে পথের সব সারে, তারপর ফেরেপ্রান্তের request বেশি অপেক্ষা করে
C-SCANএক দিকে গিয়ে শেষে সরাসরি শুরুতে ফিরে আবারআরও সুষম অপেক্ষা
💡 SSD-তে এটা কম গুরুত্বপূর্ণ এই সব অ্যালগরিদম HDD-র জন্য — যেখানে ফিজিক্যাল head movement বড় খরচ। SSD-তে কোনো head নেই, random অ্যাক্সেস প্রায় সমান দ্রুত, তাই disk scheduling-এর গুরুত্ব অনেক কম। আধুনিক OS টের পায় নিচে HDD না SSD, আর সেই অনুযায়ী কৌশল বদলায়। এটা একটা ভালো উদাহরণ — হার্ডওয়্যার বদলালে OS-এর কৌশলও বদলাতে হয়।
🧠 যাচাই করুন
SCAN অ্যালগরিদম কেন "লিফট" নামে পরিচিত?

লিফটের মতো — head এক দিকে যেতে যেতে পথের সব request সারে, প্রান্তে পৌঁছে উল্টো দিকে ফেরে। এতে অপ্রয়োজনীয় আগে-পিছে নড়াচড়া কমে।

SSTF-এ starvation কেন হতে পারে?

সবসময় কাছের request আগে সারলে, নতুন কাছের request আসতেই থাকলে দূরের একটা request কখনো সুযোগ না-ও পেতে পারে।

০৭

Buffer Cache

buffer-cache

Disk লক্ষ গুণ ধীর RAM-এর চেয়ে। তাই OS একটা সহজ কিন্তু শক্তিশালী কৌশল ব্যবহার করে: সম্প্রতি পড়া/লেখা disk block RAM-এ রেখে দেওয়া। এটাই buffer cache (বা page cache)।

🧊 উপমা — রান্নাঘরের হাতের কাছের তাক গুদাম (disk) থেকে প্রতিবার মসলা আনা ঝামেলা। তাই যেগুলো বারবার লাগে সেগুলো রান্নাঘরের হাতের কাছের তাকে (RAM cache) রাখেন। পরেরবার গুদামে না গিয়ে সাথে সাথে পান। disk block-ও তাই — একবার পড়লে RAM-এ থাকে, পরের বার সরাসরি।

দুটো বড় সুবিধা

Read caching: একবার পড়া block RAM-এ থাকে, বারবার পড়লে disk ছুঁতে হয় না। এজন্যই একটা প্রোগ্রাম দ্বিতীয়বার চালালে দ্রুত খোলে — তার ফাইল তখন cache-এ।

Write buffering: লেখা সাথে সাথে disk-এ না গিয়ে প্রথমে cache-এ জমা হয়, OS পরে একসাথে লেখে। এতে অনেক ছোট লেখা একত্র হয়, আর একই জায়গায় বারবার লিখলে শুধু শেষটা disk-এ যায়।

⚠️ Write buffering-এর ঝুঁকি — আর তাই fsync লেখা cache-এ থাকা মানে disk-এ এখনো যায়নি। এই সময় crash হলে সেই ডেটা হারিয়ে যায়! এজন্য গুরুত্বপূর্ণ ডেটায় (যেমন database একটা লেনদেন) প্রোগ্রাম fsync() ডাকে — যা OS-কে বাধ্য করে cache-এর ডেটা এখনই disk-এ লিখতে। এই কারণেই "সেভ হয়েছে" দেখানোর পরও হঠাৎ পাওয়ার গেলে কখনো শেষ কিছু কাজ হারায় — buffer এখনো disk-এ যায়নি। fsync কখন ডাকতে হবে জানা সিস্টেম প্রোগ্রামিং-এর একটা গুরুত্বপূর্ণ দক্ষতা।
🔬 গভীরে — cache কতটা RAM নেয়? Linux-এ buffer/page cache খালি RAM-এর প্রায় সবটাই ব্যবহার করে — কারণ অব্যবহৃত RAM অপচয়। এজন্য free -h চালালে দেখবেন অনেক RAM "used" কিন্তু আসলে বেশিরভাগ cache, যা দরকার হলে সাথে সাথে ছেড়ে দেওয়া হয়। "Linux আমার সব RAM খেয়ে ফেলেছে!" — এই ভয় সাধারণত ভুল বোঝাবুঝি; ওটা cache, আপনার সুবিধার জন্যই। এটাই "unused RAM is wasted RAM" নীতি।
🧠 যাচাই করুন
একটা প্রোগ্রাম দ্বিতীয়বার দ্রুত খোলে কেন?

প্রথমবার পড়ার সময় তার ফাইল buffer cache-এ চলে আসে (RAM-এ)। দ্বিতীয়বার disk ছুঁতে হয় না, সরাসরি cache থেকে — তাই দ্রুত।

fsync() কখন দরকার?

যখন নিশ্চিত হতে হবে ডেটা সত্যিই disk-এ লেখা হয়েছে (crash-এও থাকবে) — যেমন database লেনদেন। এটা buffer cache-এর ডেটা এখনই disk-এ লিখতে বাধ্য করে।

০৮

প্রজেক্ট — নিজের toy File System

build-a-filesystem

এই মডিউলের সব ধারণা একসাথে জোড়া লাগানোর সময়। একটা সাধারণ ফাইলকে "ভার্চুয়াল ডিস্ক" ধরে তার উপর একটা কাজ করা file system বানাবেন — superblock, inode, data block সহ। এটা persistence-এর সব ধারণা পাকা করবে।

🎯 মূল ধারণা — ফাইলের ভেতরে file system আসল disk নিয়ে খেলা ঝুঁকিপূর্ণ ও কঠিন। তাই কৌশল: একটা বড় সাধারণ ফাইল (যেমন disk.img, ১০ MB) তৈরি করুন — এটাই আপনার "ভার্চুয়াল ডিস্ক"। এর ভেতরটা block-এ ভাগ করুন, আর সেখানে আপনার file system-এর কাঠামো বসান। সব নিরাপদে userspace-এ চলে।

ধাপ ১ — ডিস্কের কাঠামো ঠিক করুন

// সরল লেআউট: ব্লক সাইজ 4KB ধরে
// block 0: superblock
// block 1: inode bitmap
// block 2: data bitmap
// block 3..N: inode টেবিল
// block N+1..: data blocks

#define BLOCK_SIZE 4096
#define MAX_INODES 128

typedef struct {
    int size;                // ফাইল কত byte
    int type;                // 0 = খালি, 1 = ফাইল, 2 = directory
    int blocks[12];          // direct block pointer (সরল রাখলাম)
} inode_t;

typedef struct {
    int total_blocks;
    int total_inodes;
    int data_start;          // data block কোথা থেকে শুরু
} superblock_t;

ধাপ ২ — মূল অপারেশন

🛠 যা যা implement করবেন
  1. fs_format(): disk.img তৈরি করে superblock ও খালি bitmap লেখো
  2. fs_create(name): একটা খালি inode খুঁজে (bitmap দেখে) নতুন ফাইল বানাও, root directory-তে নাম→inode যোগ করো
  3. fs_write(name, data): খালি data block বরাদ্দ করো, ডেটা লেখো, inode-এ pointer ও সাইজ আপডেট করো
  4. fs_read(name): নাম থেকে inode খুঁজে, তার block pointer ধরে ডেটা পড়ো
  5. fs_ls(): root directory-র সব এন্ট্রি দেখাও
  6. fs_delete(name): inode ও data block "খালি" চিহ্নিত করো (bitmap আপডেট), directory থেকে এন্ট্রি সরাও
🔬 এই প্রজেক্ট যা শেখায় নিজে file system লিখলে হঠাৎ পরিষ্কার হয়: কেন delete আসলে ডেটা মোছে না (শুধু bitmap-এ "খালি" চিহ্নিত করে — এজন্যই deleted ফাইল কখনো recover করা যায়!), কেন fragmentation হয় (খালি block ছড়িয়ে-ছিটিয়ে থাকে), কেন directory নিজেও একটা ফাইল, আর কেন প্রতিটা অপারেশনে একাধিক জায়গায় (bitmap + inode + data) লিখতে হয় — যা journaling-এর প্রয়োজনীয়তা বোঝায়। তত্ত্বে পড়া সব ধারণা কোডে জীবন্ত হয়ে ওঠে।
🛠 চ্যালেঞ্জ — আরও এগিয়ে
  1. Subdirectory: শুধু root নয়, nested directory সাপোর্ট করুন (/a/b/file)
  2. Indirect block: ১২ block-এর বেশি বড় ফাইলের জন্য single indirect যোগ করুন
  3. Persistence যাচাই: প্রোগ্রাম বন্ধ করে আবার চালিয়ে দেখুন ফাইল টিকে আছে (আসল persistence!)
  4. FUSE দিয়ে mount: libfuse ব্যবহার করে আপনার FS-কে সত্যিকারের mount করুন — ls, cat দিয়ে ব্যবহার করুন যেন আসল file system!
🛠 আসল file system পরীক্ষা করুন নিজেরটা বানানোর পাশাপাশি Linux টুল দিয়ে আসলটা দেখুন: stat file.txt (inode-এর তথ্য), ls -i (inode নম্বর), df (disk ব্যবহার), du (ফাইলের সাইজ)। stat-এর আউটপুটে inode নম্বর, block সংখ্যা, link count — সব এই মডিউলে শেখা জিনিস চিনতে পারবেন।
🎓 মডিউল ৫ শেষ — তিন স্তম্ভ সম্পূর্ণ! আপনি এখন জানেন disk কেন ধীর, file ও directory কীভাবে block-এর উপর তৈরি হয়, inode কী, একটা ফাইল খোঁজার পুরো যাত্রা, journaling কীভাবে crash থেকে বাঁচায়, disk scheduling, buffer cache — আর নিজে একটা file system বানিয়েছেন।
