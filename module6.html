নিজের OS
বানানো

এতদিন যা যা শিখেছেন — process, memory, concurrency, file system — এবার সেসব একটা আসল, চলমান kernel-এ দেখবেন। xv6 পড়ে, পরিবর্তন করে, আর নতুন feature যোগ করে আপনি "বুঝেছি" থেকে "পারি"-তে পৌঁছাবেন।

০০

শুরুর কথা

orientation

এটাই যাত্রার শেষ ধাপ, আর সবচেয়ে ফলদায়ক। এতদিন প্রতিটা ধারণা আলাদা করে শিখেছেন আর ছোট প্রজেক্টে দেখেছেন। এবার একটা সম্পূর্ণ OS-এ সব একসাথে কীভাবে জোড়া লাগে দেখবেন — আর নিজে সেই kernel পরিবর্তন করবেন।

🧭 এই মডিউল আগেরগুলো থেকে আলাদা আগের মডিউলগুলো ছিল ধারণা + ছোট প্রজেক্ট। এটা মূলত একটা পথনির্দেশ — কারণ আসল kernel hacking-এর সেরা উপায় হলো MIT-র তৈরি করা lab অনুসরণ করা। আমি এখানে xv6-এর মূল ধারণা, কীভাবে শুরু করবেন, প্রথম কয়েকটা পরিবর্তন কীভাবে করবেন — সব দেখাবো, যাতে MIT 6.1810-এ ঢুকতে সহজ হয়। এটা মানচিত্র; আসল অভিযান আপনার।
⚠️ আগের মডিউলগুলো আগে শেষ করুন এই মডিউল ধরে নেয় আপনি process (মডিউল ২), memory/paging (মডিউল ৩), আর file system (মডিউল ৫) বুঝেছেন — কারণ xv6-এ এই সবকিছুর আসল বাস্তবায়ন একসাথে দেখবেন। যদি কোনোটা ঝাপসা থাকে, ফিরে গিয়ে ঝালিয়ে নিন। এখানে সব একসাথে আসবে।
০১

কেন xv6?

why-xv6

Linux kernel-এর কোড লক্ষ লক্ষ লাইন — একজন শিক্ষার্থীর পক্ষে বোঝা অসম্ভব। তাই MIT একটা ছোট, শিক্ষামূলক OS বানিয়েছে: xv6। এটাই kernel শেখার আদর্শ প্রবেশপথ।

📦 xv6 কী xv6 হলো MIT-র তৈরি একটা ছোট UNIX-সদৃশ operating system, শিক্ষার জন্য। এটা ১৯৭০-এর Unix V6-এর একটা আধুনিক পুনর্লিখন, চলে RISC-V প্রসেসরে (QEMU emulator-এ)। পুরো কোড মাত্র ~৯০০০ লাইন — একজন মানুষ কয়েক সপ্তাহে পুরোটা পড়ে বুঝতে পারে। অথচ এতে একটা আসল OS-এর সব মূল অংশ আছে: process, scheduling, virtual memory, system call, interrupt, file system।
🚗 উপমা — শেখার গাড়ি আপনি ফর্মুলা-১ গাড়ি দিয়ে ড্রাইভিং শেখেন না — একটা সরল গাড়ি দিয়ে শেখেন, যার প্রতিটা অংশ বোঝা যায়। Linux হলো ফর্মুলা-১ (শক্তিশালী কিন্তু বিশাল ও জটিল); xv6 হলো সেই শেখার গাড়ি — ছোট, সরল, প্রতিটা অংশ দেখা যায়। শেখার পর ফর্মুলা-১ (Linux) বোঝা সহজ হয়।

xv6-এ আগের মডিউলগুলো যেভাবে ফিরে আসে

আপনি শিখেছেনxv6-এ যেখানে দেখবেন
Process, fork/exec (মডিউল ২)proc.c, exec.c
Scheduling (মডিউল ২)proc.c-এর scheduler()
Virtual memory, paging (মডিউল ৩)vm.c, kalloc.c
Lock, concurrency (মডিউল ৪)spinlock.c, sleeplock.c
File system, inode (মডিউল ৫)fs.c, file.c
System call, trap (মডিউল ১)syscall.c, trap.c
💡 এটাই সবচেয়ে বড় প্রাপ্তি এতদিন ধারণাগুলো আলাদা আলাদা শিখেছেন। xv6-এ দেখবেন সেগুলো একটা বাস্তব সিস্টেমে কীভাবে একসাথে কাজ করে — কীভাবে fork একটা নতুন page table বানায়, কীভাবে system call trap-এ পরিণত হয়, কীভাবে file system lock ব্যবহার করে। বিচ্ছিন্ন টুকরোগুলো হঠাৎ একটা সম্পূর্ণ ছবিতে জোড়া লাগবে।
🧠 যাচাই করুন
Linux-এর বদলে xv6 দিয়ে শেখা কেন ভালো?

Linux লক্ষ লক্ষ লাইন — একজনের পক্ষে বোঝা অসম্ভব। xv6 মাত্র ~৯০০০ লাইন, কিন্তু একটা আসল OS-এর সব মূল অংশ আছে। তাই পুরোটা পড়ে বোঝা সম্ভব।

০২

xv6 চালানো

running-xv6

তত্ত্ব যথেষ্ট — এবার xv6 নিজের মেশিনে চালিয়ে দেখি। ভালো খবর: কোনো আসল হার্ডওয়্যার বা আলাদা মেশিন লাগবে না, সবকিছু QEMU emulator-এ চলে।

🛠 ধাপ ১ — টুল ইনস্টল RISC-V compiler ও QEMU দরকার। Ubuntu/WSL2-তে: 
sudo apt update
sudo apt install git build-essential gdb-multiarch qemu-system-misc \
     gcc-riscv64-linux-gnu binutils-riscv64-linux-gnu
(Mac-এ Homebrew দিয়ে riscv toolchain ও qemu; MIT-র সাইটে বিস্তারিত নির্দেশ আছে।)
🛠 ধাপ ২ — কোড নামিয়ে চালান 
# MIT-র xv6 (RISC-V সংস্করণ) নামান
git clone https://github.com/mit-pdos/xv6-riscv.git
cd xv6-riscv

# compile করে QEMU-তে চালান
make qemu
কিছুক্ষণ পর দেখবেন xv6 boot হচ্ছে, আর একটা shell prompt আসছে: 
xv6 kernel is booting

init: starting sh
$
এটা আপনার নিজের মেশিনে চলা একটা সম্পূর্ণ OS! ls, cat, echo চালিয়ে দেখুন।
🚪 QEMU থেকে বেরোনো QEMU বন্ধ করতে: Ctrl+A চাপুন, ছেড়ে দিন, তারপর x। (প্রথমবার অনেকে আটকে যায় — এটা মনে রাখুন!)
🔬 কী ঘটল — মডিউল ১-এর boot মনে আছে? make qemu দিলে: QEMU একটা virtual RISC-V কম্পিউটার তৈরি করে, xv6 kernel সেখানে boot করে (মডিউল ১-এর boot process — এখানে QEMU firmware → kernel), kernel প্রথম process init চালায় (PID 1, মডিউল ২-র মতো), init একটা shell চালায় (sh, ঠিক আপনার মডিউল ২ প্রজেক্টের মতো!)। আপনি যে shell বানিয়েছিলেন, xv6-এর sh.c তার-ই একটা পূর্ণ সংস্করণ — পড়ে দেখুন, চেনা লাগবে।
🧠 যাচাই করুন
xv6 চালাতে আসল হার্ডওয়্যার লাগে?

না — QEMU একটা virtual RISC-V কম্পিউটার emulate করে, তার উপর xv6 চলে। সব আপনার সাধারণ মেশিনেই।

০৩

xv6-এর গঠন

xv6-structure

কোড পরিবর্তন করার আগে জানা দরকার কোথায় কী আছে। xv6-এর কোড পরিষ্কারভাবে সাজানো — প্রতিটা ফাইলের একটা নির্দিষ্ট দায়িত্ব।

মূল ফাইলগুলো (kernel/ ফোল্ডারে)

ফাইলদায়িত্বমডিউল
proc.cprocess, fork, scheduler, context switch২
exec.cনতুন প্রোগ্রাম লোড করা (exec)২
vm.cvirtual memory, page table৩
kalloc.cphysical memory বরাদ্দ (page allocator)৩
trap.cinterrupt, trap, system call এন্ট্রি১
syscall.csystem call টেবিল ও dispatch১
sysproc.cprocess-সম্পর্কিত syscall বাস্তবায়ন২
fs.cfile system (inode, block)৫
file.cfile descriptor স্তর৫
spinlock.clock (concurrency)৪
🛠 প্রথমে যা পড়বেন পুরো kernel একবারে পড়তে যাবেন না। এই ক্রমে শুরু করুন: (১) user/sh.c — চেনা shell, আপনার প্রজেক্টের মতো। (২) user/ls.c — একটা সরল user প্রোগ্রাম। (৩) kernel/proc.h — process struct (আপনার PCB!)। (৪) kernel/syscall.c — কীভাবে syscall dispatch হয়। ছোট, চেনা জিনিস দিয়ে শুরু করলে আত্মবিশ্বাস আসে।
📖 সঙ্গী বই MIT একটা বিনামূল্যে বই দেয় — "xv6: a simple, Unix-like teaching operating system" (PDF)। এটা xv6-এর কোড লাইন ধরে ধরে ব্যাখ্যা করে। কোড পড়ার পাশে এই বই রাখুন — কোন অংশ কী করছে বুঝতে অমূল্য। এটাই xv6 শেখার সরকারি গাইড।
🧠 যাচাই করুন
process struct (PCB) xv6-এর কোথায়?

kernel/proc.h-এ struct proc। এটাই মডিউল ২-তে শেখা PCB-র আসল বাস্তবায়ন — state, page table, trapframe, খোলা ফাইল সব এখানে।

xv6 পড়া শুরু করার ভালো জায়গা কোথায়?

চেনা user প্রোগ্রাম দিয়ে — sh.c (shell), ls.c। তারপর ধীরে ধীরে kernel-এ (proc.h, syscall.c)। ছোট চেনা জিনিস থেকে বড় দিকে।

০৪

নতুন System Call যোগ করা

adding-a-syscall

এটাই প্রথম আসল kernel hacking — আর সবচেয়ে শিক্ষণীয়। একটা নতুন system call যোগ করে আপনি দেখবেন user প্রোগ্রাম থেকে kernel পর্যন্ত পুরো পথটা কীভাবে জোড়া। মডিউল ১-এর system call তত্ত্ব এখানে হাতে-কলমে।

🎯 লক্ষ্য — একটা সরল syscall ধরা যাক আমরা একটা getreadcount() syscall বানাবো, যা বলবে বুট হওয়ার পর কতবার read syscall ডাকা হয়েছে। সরল, কিন্তু এটা করতে গিয়ে syscall-এর পুরো শৃঙ্খল ছুঁতে হবে — সেটাই আসল শিক্ষা।

একটা syscall যোগ করতে যে ফাইলগুলো ছুঁতে হয়

ধাপে ধাপে

🛠 পাঁচটা ধাপ ১. user/user.h: syscall-এর ঘোষণা যোগ করুন যাতে user প্রোগ্রাম ডাকতে পারে: 
int getreadcount(void);
২. user/usys.pl: একটা এন্ট্রি যোগ করুন (এই perl script user-side stub তৈরি করে, যা আসলে trap ঘটায়): 
entry("getreadcount");
৩. kernel/syscall.h: একটা নতুন syscall নম্বর দিন: 
#define SYS_getreadcount 22
৪. kernel/syscall.c: dispatch টেবিলে যোগ করুন (আর extern ঘোষণা): 
extern uint64 sys_getreadcount(void);
// syscalls[] টেবিলে:
[SYS_getreadcount] sys_getreadcount,
৫. kernel/sysproc.c: আসল কাজটা লিখুন: 
uint64
sys_getreadcount(void) {
    return readcount;   // একটা global counter
}
(আর read-এর বাস্তবায়নে readcount++ যোগ করতে হবে।)
🛠 পরীক্ষা করুন একটা ছোট user প্রোগ্রাম লিখুন (user/rctest.c) যা getreadcount() ডাকে ও প্রিন্ট করে, Makefile-এ যোগ করুন (UPROGS তালিকায়), make qemu দিয়ে চালান। xv6 prompt-এ rctest চালালে read count দেখবেন — আপনার নিজের বানানো syscall কাজ করছে!
🔬 গভীরে — আপনি ঠিক কী করলেন এই ছোট কাজটায় মডিউল ১-এর পুরো তত্ত্ব জীবন্ত হলো: user প্রোগ্রাম getreadcount() ডাকল → usys.pl-এর তৈরি stub একটা ecall instruction চালাল (RISC-V-এর trap, মডিউল ১) → CPU kernel mode-এ গেল, trap.c-এ পৌঁছাল → syscall.c নম্বর দেখে সঠিক function খুঁজল → sys_getreadcount() চলল → ফল register-এ রেখে user mode-এ ফিরল। মডিউল ১-এ যে "system call = নিয়ন্ত্রিত দরজা" শিখেছিলেন, তার প্রতিটা ইট এখানে ছুঁয়েছেন।
🧠 যাচাই করুন
একটা syscall যোগ করতে কেন এতগুলো ফাইল ছুঁতে হয়?

কারণ syscall user ও kernel-এর সীমানা পার করে — user-side stub (ঘোষণা, trap ঘটানো), একটা নম্বর (kernel চেনার জন্য), dispatch টেবিল (নম্বর→function), আর আসল বাস্তবায়ন। পুরো পথটাই সংযুক্ত করতে হয়।

user প্রোগ্রামের syscall কীভাবে kernel-এ পৌঁছায়?

usys.pl-এর তৈরি stub একটা trap instruction (ecall) চালায়, যা CPU-কে kernel mode-এ নিয়ে trap handler-এ পাঠায়। সেখান থেকে syscall.c নম্বর দেখে সঠিক function ডাকে।

০৫

Scheduler বদলানো

changing-the-scheduler

দ্বিতীয় ক্লাসিক kernel hack — scheduler পরিবর্তন। xv6 ডিফল্টে একটা সরল round-robin ব্যবহার করে। এটা বদলে আপনি মডিউল ২-এর scheduling তত্ত্ব বাস্তবে প্রয়োগ করবেন।

🔍 xv6-এর বর্তমান scheduler kernel/proc.c-এর scheduler() function দেখুন — এটা আশ্চর্যজনকভাবে সরল। এটা শুধু process টেবিল ধরে ধরে ঘোরে, একটা RUNNABLE process পেলে তাকে চালায়, timer interrupt এলে পরেরটায় যায়। এটাই বিশুদ্ধ round-robin (মডিউল ২)। মাত্র কয়েক লাইন কোড!
🛠 প্রজেক্ট — priority scheduling যোগ করুন
  1. struct proc-এ (proc.h) একটা priority ফিল্ড যোগ করুন
  2. একটা নতuন syscall setpriority(int) বানান (অধ্যায় ৪-এর পদ্ধতিতে) — process নিজের priority সেট করতে পারবে
  3. scheduler() বদলান — শুধু পরেরটা না নিয়ে, সবচেয়ে উঁচু priority-র RUNNABLE process বাছুন
  4. পরীক্ষা করুন: ভিন্ন priority-র কয়েকটা process চালিয়ে দেখুন উঁচুটা বেশি CPU পাচ্ছে
🔬 আরও উচ্চাভিলাষী — MLFQ বা Lottery আত্মবিশ্বাস এলে মডিউল ২-এর উন্নত scheduler বাস্তবায়ন করুন। Lottery scheduling: প্রতিটা process কিছু "টিকিট" পায়, scheduler এলোমেলোভাবে একটা টিকিট তোলে — বেশি টিকিট = বেশি সুযোগ, কিন্তু কেউ পুরোপুরি বঞ্চিত হয় না। বাস্তবায়ন সহজ ও মার্জিত। MLFQ: কয়েকটা priority queue, আচরণ দেখে priority সমন্বয় (মডিউল ২)। এগুলো MIT 6.1810-র বাইরের চ্যালেঞ্জ, কিন্তু অসাধারণ শেখায় — কারণ আপনাকে scheduler, timer interrupt, আর process state একসাথে সামলাতে হবে।
⚠️ এখানে lock-এর কথা মনে রাখুন Scheduler ছোঁয়া মানে concurrency-র গভীরে ঢোকা (মডিউল ৪)। process টেবিল একটা শেয়ার্ড রিসোর্স — একাধিক CPU একসাথে scheduler চালায়। তাই xv6-এ প্রতিটা process-এর একটা lock আছে, আর scheduler সেগুলো সাবধানে নেয়-ছাড়ে। কোড বদলানোর সময় lock-এর নিয়ম না মানলে race condition বা deadlock হবে। মডিউল ৪ এখানে সরাসরি কাজে লাগবে — এটাই সব একসাথে আসার জায়গা।
🧠 যাচাই করুন
xv6-এর ডিফল্ট scheduler কোন অ্যালগরিদম?

সরল round-robin — process টেবিল ধরে ঘোরে, প্রতিটা RUNNABLE process-কে পালা করে সুযোগ দেয়, timer interrupt-এ পরেরটায় যায়।

Scheduler বদলাতে গেলে কেন concurrency সাবধানতা লাগে?

process টেবিল একাধিক CPU-র শেয়ার্ড রিসোর্স। lock ঠিকমতো ব্যবহার না করলে race condition বা deadlock হবে (মডিউল ৪)। xv6-এর lock নিয়ম মেনে চলতে হয়।

০৬

GDB দিয়ে Kernel Debug করা

debugging-with-gdb

Kernel-এ বাগ ধরা কঠিন — printf সবসময় যথেষ্ট নয়। ভালো খবর: QEMU + GDB দিয়ে আপনি চলন্ত kernel-কে থামিয়ে, লাইন ধরে ধরে দেখতে পারেন কী ঘটছে। এটা kernel hacking-এর অপরিহার্য দক্ষতা।

🛠 GDB চালু করা দুটো টার্মিনাল লাগবে। প্রথমটায়: 
make qemu-gdb
এটা xv6 চালু করে কিন্তু GDB-র সংযোগের জন্য অপেক্ষা করে। দ্বিতীয় টার্মিনালে (xv6-riscv ফোল্ডারে): 
gdb-multiarch kernel/kernel
এখন GDB kernel-এর সাথে যুক্ত — breakpoint বসাতে, variable দেখতে, লাইন ধরে চলতে পারবেন।
🛠 কাজের GDB কমান্ড 
break syscall          # syscall function-এ থামো
continue               # চলতে দাও (breakpoint পর্যন্ত)
next / step            # এক লাইন এগোও
print p->pid           # একটা variable দেখো
backtrace              # কোন পথে এখানে এলাম
info registers         # সব register
যেমন — অধ্যায় ৪-এর নিজের syscall-এ breakpoint বসিয়ে দেখুন সত্যিই সেখানে পৌঁছাচ্ছে কিনা, argument কী আসছে।
🔬 কেন এটা এত শক্তিশালী এতদিন যা তত্ত্বে পড়েছেন — context switch, page table, trap — GDB দিয়ে সেগুলো ঘটতে দেখতে পারবেন। swtch (context switch) function-এ breakpoint বসিয়ে register-এর মান দেখুন প্রক্রিয়ার আগে-পরে; trap handler-এ থেমে দেখুন trapframe-এ কী সংরক্ষিত হলো। তত্ত্বকে চোখের সামনে ঘটতে দেখা — এর চেয়ে ভালো শেখার উপায় নেই। বাস্তব চাকরিতেও kernel/systems debugging-এ এই দক্ষতা অমূল্য।
🧠 যাচাই করুন
kernel debug করতে দুটো টার্মিনাল কেন লাগে?

একটায় QEMU kernel চালায় (এবং GDB-র সংযোগের অপেক্ষা করে), আরেকটায় GDB সেই চলন্ত kernel-এর সাথে যুক্ত হয়ে নিয়ন্ত্রণ করে (breakpoint, লাইন-বাই-লাইন)।

০৭

MIT 6.1810-র পথ

the-mit-path

এতক্ষণ যা শিখলেন তা আপনাকে xv6-এ ঢোকার প্রস্তুতি দিয়েছে। এবার আসল, কাঠামোবদ্ধ পথ — MIT-র 6.1810 কোর্স, যা পুরোপুরি বিনামূল্যে ও অনলাইনে উন্মুক্ত।

🎓 MIT 6.1810 কী এটা MIT-র স্নাতক operating systems কোর্স (আগে 6.828 নামে পরিচিত)। এর সব উপকরণ উন্মুক্ত: লেকচার নোট, xv6 বই, আর — সবচেয়ে গুরুত্বপূর্ণ — একগুচ্ছ lab, যেখানে আপনি xv6-এ ধাপে ধাপে feature যোগ করেন। এগুলোই বিশ্বের হাজার হাজার শিক্ষার্থীর kernel শেখার পথ।

  1. "MIT 6.1810" খুঁজুন (সাম্প্রতিকতম সংস্করণের সাইট) — সব উন্মুক্ত
  2. Lab পেজে যান, util lab দিয়ে শুরু করুন (git branch দেওয়া থাকে)
  3. প্রতিটা lab-এর সাথে সংশ্লিষ্ট লেকচার ও xv6 বইয়ের অধ্যায় পড়ুন
  4. ধৈর্য ধরুন — একটা lab কয়েক দিন লাগতে পারে, এটাই স্বাভাবিক
⚠️ একটা পরামর্শ — আটকানো স্বাভাবিক Kernel lab কঠিন। ঘণ্টার পর ঘণ্টা একটা বাগে আটকে থাকা এই যাত্রার অংশ — লজ্জার কিছু নয়, বরং এখানেই সবচেয়ে গভীর শেখা হয়। GDB ব্যবহার করুন (অধ্যায় ৬), xv6 বই আবার পড়ুন, কোড আরেকবার মন দিয়ে দেখুন। প্রতিটা কঠিন বাগ পার হওয়ার পর আপনি আগের চেয়ে অনেক শক্তিশালী প্রোগ্রামার। "যা বানাতে পারবেন না, তা বুঝেছেন বলে ধরবেন না" — রোডম্যাপের এই কথাটাই এখানে সবচেয়ে সত্য।
🧠 যাচাই করুন
MIT 6.1810-র lab-গুলো কীসের উপর ভিত্তি করে?

xv6-এর উপর। প্রতিটা lab-এ xv6-এ ধাপে ধাপে feature যোগ করতে হয় — syscall, page table, lock, file system ইত্যাদি — যা আপনার এই ৬ মডিউলের ধারণার সরাসরি প্রয়োগ।

💡 কিন্তু আসল লাভ অন্যখানে এই জ্ঞানের সবচেয়ে বড় মূল্য হয়তো নিজে OS বানানো নয় — বরং বাকি সব কিছু ভালো বোঝা। এখন আপনি জানেন কেন একটা প্রোগ্রাম ধীর (cache miss, page fault, context switch), কেন multithreaded কোডে অদ্ভুত বাগ (race condition), কেন database এভাবে ডিজাইন (journaling, fsync), কীভাবে কন্টেইনার কাজ করে (namespace, cgroup)। এই "নিচের স্তর দেখতে পারা"-ই আপনাকে অন্যদের থেকে আলাদা করবে — সিস্টেম ডিজাইন, ডিবাগিং, পারফরম্যান্স, সবখানে।
🔬 বাস্তব জগতে এই জ্ঞান যেসব জায়গায় এই OS জ্ঞান সরাসরি কাজে লাগে: ব্যাকএন্ড ইঞ্জিনিয়ারিং (concurrency, memory, I/O টিউনিং), DevOps/SRE (কন্টেইনার, cgroup, সিস্টেম ডিবাগিং), ডেটাবেস (storage engine, journaling, buffer cache), embedded/IoT (RTOS, সীমিত সম্পদ), নিরাপত্তা (privilege, memory protection), ক্লাউড অবকাঠামো (virtualization, hypervisor)। OS বোঝা মানে computing-এর মেরুদণ্ড বোঝা।
