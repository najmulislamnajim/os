অপারেটিং সিস্টেমের
ভিত্তি

OS আসলে কী কাজ করে, হার্ডওয়্যারের সাথে কীভাবে কথা বলে, আর আপনার প্রোগ্রাম কীভাবে kernel-এর সাহায্য চায় — সব একদম গোড়া থেকে। এই মডিউলই বাকি সব মডিউলের ভিত্তি।

০০

শুরুর কথা

orientation

রোডম্যাপে দেখেছি OS তিনটা বড় ধারণার চারপাশে ঘোরে — Virtualization, Concurrency, Persistence। কিন্তু এসবের আগে বুঝতে হবে OS জিনিসটা কী, আর সে হার্ডওয়্যারের সাথে কীভাবে কাজ করে।

📐 বাক্সের ধরন কমলা (উপমা): দৈনন্দিন জীবনের মিল। সবুজ (ল্যাব): নিজে হাতে করার প্রজেক্ট। বেগুনি (গভীরে): বেশি প্রযুক্তিগত। নীল (নোট): জরুরি তথ্য। লালচে (সতর্কতা): সাধারণ ভুল।
🛠 আগে পরিবেশ ঠিক করুন এই মডিউলের কোড চালাতে একটা Linux পরিবেশ লাগবে। Windows-এ wsl --install দিয়ে WSL2 বসান; Mac-এ বেশিরভাগ চলবে তবে strace-এর জন্য একটা Linux VM ভালো। থাকলে gcc, strace, gdb ইনস্টল করে নিন: sudo apt install gcc strace gdb
০১

অপারেটিং সিস্টেম আসলে কী?

what-is-an-os

আপনি যখন একটা প্রোগ্রাম চালান, সেটা সরাসরি হার্ডওয়্যারে চলে না। মাঝখানে একজন মধ্যস্থতাকারী থাকে — অপারেটিং সিস্টেম। তার দুটো প্রধান কাজ।

🏨 উপমা — হোটেলের ব্যবস্থাপক একটা হোটেলে অনেক অতিথি (প্রোগ্রাম), কিন্তু সীমিত রুম, লিফট, রান্নাঘর (হার্ডওয়্যার)। প্রতিটা অতিথি যদি সরাসরি রান্নাঘরে ঢুকে নিজের রান্না করতে চায়, বিশৃঙ্খলা হবে। তাই একজন ব্যবস্থাপক (OS) থাকে — সে ঠিক করে কে কোন রুম পাবে, কখন লিফট ব্যবহার করবে, আর কেউ যেন আরেকজনের রুমে ঢুকতে না পারে। অতিথিকে শুধু ব্যবস্থাপকের কাছে চাইতে হয়, বাকিটা সে সামলায়।

OS-এর দুই প্রধান ভূমিকা

১. Resource Manager — সম্পদ ব্যবস্থাপক

CPU, RAM, disk, নেটওয়ার্ক কার্ড — এগুলো সীমিত সম্পদ। অনেকগুলো প্রোগ্রাম একসাথে এগুলো চায়। OS ঠিক করে কে কখন কতটুকু পাবে, যাতে সবাই সুষ্ঠুভাবে চলে আর কেউ সব দখল করে না ফেলে।

২. Hardware Abstraction — হার্ডওয়্যার আড়াল করা

পৃথিবীতে হাজার রকম হার্ডওয়্যার — ভিন্ন ভিন্ন কোম্পানির disk, keyboard, GPU। প্রতিটা প্রোগ্রাম যদি প্রতিটা হার্ডওয়্যারের নিজস্ব ভাষা শিখতে হতো, প্রোগ্রামিং অসম্ভব হয়ে যেত। OS একটা সহজ, অভিন্ন ইন্টারফেস দেয় — আপনি শুধু write() বলেন, কোন ব্র্যান্ডের disk তা OS সামলায়।

💡 মূল অন্তর্দৃষ্টি OS আসলে একটা প্রোগ্রাম — কিন্তু একটা বিশেষ প্রোগ্রাম যার হার্ডওয়্যারের উপর পূর্ণ নিয়ন্ত্রণ আছে। বাকি সব প্রোগ্রাম তার অনুমতি নিয়ে চলে। এই "বিশেষ ক্ষমতা"-র ব্যাপারটাই পরের অধ্যায়ের বিষয়।

🧠 যাচাই করুন
OS-এর দুটো প্রধান কাজ কী?

(১) Resource manager — সীমিত হার্ডওয়্যার সম্পদ প্রোগ্রামগুলোর মধ্যে ভাগ করা। (২) Hardware abstraction — বিভিন্ন হার্ডওয়্যারকে একটা সহজ, অভিন্ন ইন্টারফেসের আড়ালে লুকানো।

একটা প্রোগ্রাম কি সরাসরি disk-এ লিখতে পারে?

না — তাকে OS-এর কাছে write() দিয়ে চাইতে হয়। OS-ই আসল হার্ডওয়্যার নিয়ন্ত্রণ করে। এটাই নিরাপত্তা ও শৃঙ্খলার ভিত্তি।

০২

Kernel ও User Space

kernel-vs-user

এটা OS-এর সবচেয়ে মৌলিক ধারণা। CPU দুটো আলাদা "মোডে" চলতে পারে, আর এই দুই মোডের বিভাজনই আধুনিক কম্পিউটিং-এর নিরাপত্তার ভিত্তি।

🔑 উপমা — ব্যাংকের কর্মী বনাম গ্রাহক ব্যাংকে গ্রাহক (user) কাউন্টারের সামনে দাঁড়িয়ে অনুরোধ করে — "৫০০০ টাকা তুলবো"। সে নিজে ভল্টে ঢুকতে পারে না। শুধু কর্মী (kernel) ভল্টে ঢোকার অধিকার রাখে। গ্রাহক চাইলে কর্মী যাচাই করে কাজটা করে দেয়। এভাবে ভল্ট (হার্ডওয়্যার) নিরাপদ থাকে — যে কেউ ইচ্ছেমতো ঢুকতে পারে না।

🔬 গভীরে — CPU কীভাবে মোড জানে? CPU-র ভেতরে একটা বিশেষ বিট থাকে (x86-এ একে বলে "ring level" — ring 0 = kernel, ring 3 = user)। কিছু instruction (যেমন সরাসরি disk-এ লেখা, interrupt নিয়ন্ত্রণ করা) শুধু ring 0-তে চলে। User mode-এ থাকা প্রোগ্রাম যদি এই "privileged instruction" চালানোর চেষ্টা করে, CPU সাথে সাথে একটা exception তোলে আর OS প্রোগ্রামটাকে থামিয়ে দেয়। এই হার্ডওয়্যার-স্তরের বাধাই নিরাপত্তার আসল ভিত্তি — এটা সফটওয়্যার দিয়ে বাইপাস করা যায় না।
💡 কেন এই বিভাজন এত গুরুত্বপূর্ণ? এই দুই-মোডের ব্যবস্থা না থাকলে যেকোনো প্রোগ্রাম যেকোনো সময় পুরো সিস্টেম নিয়ন্ত্রণ করতে পারত — একটা বাগি প্রোগ্রাম বা ভাইরাস পুরো মেশিন দখল করে নিত। এই বিভাজনের কারণেই একটা প্রোগ্রাম ক্র্যাশ করলে শুধু সেটাই বন্ধ হয়, পুরো কম্পিউটার নয়।
🧠 যাচাই করুন
User mode-এ একটা প্রোগ্রাম সরাসরি হার্ডওয়্যার ছুঁতে চাইলে কী হয়?

CPU একটা exception তোলে, আর OS প্রোগ্রামটাকে থামিয়ে দেয় (সাধারণত segmentation fault বা অনুরূপ)। privileged instruction শুধু kernel mode-এ চলে।

Kernel-এ বাগ থাকলে আর user প্রোগ্রামে বাগ থাকলে — পার্থক্য?

User প্রোগ্রামের বাগে শুধু সেই প্রোগ্রাম ক্র্যাশ করে। Kernel-এর বাগে পুরো সিস্টেম ক্র্যাশ করতে পারে (kernel panic / BSOD), কারণ kernel-এর পূর্ণ ক্ষমতা।

০৩

System Call — kernel-এর দরজা

system-calls

User প্রোগ্রাম নিজে হার্ডওয়্যার ছুঁতে পারে না। তাহলে ফাইল পড়বে কীভাবে, নেটওয়ার্কে পাঠাবে কীভাবে? উত্তর — system call। এটাই user space থেকে kernel-এ ঢোকার একমাত্র বৈধ দরজা।

🪟 উপমা — অফিসের সার্ভিস উইন্ডো সরকারি অফিসে আপনি ভেতরে ঢুকতে পারেন না, কিন্তু একটা নির্দিষ্ট জানালা আছে। সেখানে গিয়ে নির্দিষ্ট ফর্ম পূরণ করে অনুরোধ করেন। ভেতরের কর্মী যাচাই করে কাজটা করে ফলাফল ফিরিয়ে দেয়। System call হলো সেই জানালা — নির্দিষ্ট কিছু অনুরোধ, নির্দিষ্ট নিয়মে।

একটা system call-এ ঠিক কী ঘটে

আপনি যখন C-তে printf("Hello") লেখেন, তার নিচে শেষ পর্যন্ত একটা write() system call ঘটে। ধাপগুলো দেখুন:

🔬 গভীরে — "trap" জিনিসটা কী? System call আসলে একটা নিয়ন্ত্রিত "trap" — একটা বিশেষ CPU instruction (x86-64 Linux-এ syscall)। এটা চালালে CPU নিজে থেকে kernel mode-এ চলে যায় আর একটা পূর্বনির্ধারিত জায়গায় (system call handler) লাফ দেয়। প্রোগ্রাম একটা সংখ্যা দিয়ে বলে কোন syscall চায় (যেমন Linux x86-64-এ write = 1), আর register-এ argument রাখে। এই পুরো প্রক্রিয়াটা হার্ডওয়্যার + OS মিলে নিয়ন্ত্রণ করে, তাই user প্রোগ্রাম "ইচ্ছেমতো" kernel-এ ঢুকতে পারে না — শুধু এই নির্দিষ্ট দরজা দিয়ে।
⚠️ system call ব্যয়বহুল Mode switch-এ খরচ আছে — register সংরক্ষণ, mode বদল, cache-এর প্রভাব। এজন্য বেশি system call = ধীর প্রোগ্রাম। এই কারণেই printf ভেতরে ডেটা buffer করে রাখে আর একবারে অনেকটা লেখে, প্রতিটা অক্ষরে আলাদা write() করে না। পরের প্রজেক্টে strace দিয়ে এটা নিজ চোখে দেখবেন।
🧠 যাচাই করুন
System call কেন দরকar, প্রোগ্রাম সরাসরি কাজ করলেই তো হয়?

কারণ user প্রোগ্রামের হার্ডওয়্যার ছোঁয়ার অধিকার নেই (নিরাপত্তা)। System call হলো নিয়ন্ত্রিত একটা দরজা, যেখানে kernel অনুরোধ যাচাই করে নিরাপদে কাজটা করে দেয়।

printf কেন সরাসরি প্রতি অক্ষরে write() করে না?

System call ব্যয়বহুল (mode switch)। তাই printf ডেটা buffer করে একবারে লেখে — performance বাঁচাতে।

০৪

Interrupt ও Trap

interrupts-and-traps

CPU একটা সময়ে একটা কাজ করে। কিন্তু keyboard চাপলে, নেটওয়ার্কে প্যাকেট এলে, বা timer বেজে উঠলে — CPU কীভাবে জানে? সে বারবার জিজ্ঞেস করে না; বরং হার্ডওয়্যার তাকে interrupt দিয়ে ডাকে।

🔔 উপমা — কলিং বেল বনাম বারবার দরজা দেখা আপনি কাজ করছেন। অতিথি এলো কিনা জানতে দুটো উপায়: (১) প্রতি মিনিটে উঠে দরজা দেখা — সময়ের অপচয় (একে বলে polling); (২) একটা কলিং বেল লাগানো — অতিথি এলে বেল বাজবে, আপনি তখনই যাবেন (এটাই interrupt)। CPU দ্বিতীয় পদ্ধতি ব্যবহার করে — কাজ করতে থাকে, দরকার হলে হার্ডওয়্যার "বেল বাজায়"।

তিন ধরনের "বাধা"

ধরনউৎসউদাহরণ
Interrupt (hardware)বাইরের ডিভাইসkeyboard চাপ, প্যাকেট আসা, timer
Trap (software)প্রোগ্রাম নিজে ইচ্ছাকৃতsystem call
Exception / Faultপ্রোগ্রামের ভুলশূন্য দিয়ে ভাগ, ভুল memory অ্যাক্সেস

Interrupt এলে কী ঘটে

CPU বর্তমান কাজ থামায়, বর্তমান অবস্থা (register) সংরক্ষণ করে, kernel-এর একটা নির্দিষ্ট interrupt handler-এ লাফ দেয়, সেটা কাজ সারে, তারপর CPU আগের জায়গায় ফিরে যেন কিছুই হয়নি এমনভাবে কাজ চালিয়ে যায়।

⏰ Timer interrupt — OS-এর সবচেয়ে জরুরি interrupt একটা হার্ডওয়্যার timer নিয়মিত (যেমন প্রতি ১০ মিলিসেকেন্ডে) CPU-কে interrupt করে। এটাই OS-কে নিয়ন্ত্রণ ফিরিয়ে দেয় — নাহলে একটা প্রোগ্রাম CPU দখল করে বসে থাকলে OS কখনো তাকে থামাতে পারত না। এই timer interrupt-ই multitasking-এর ভিত্তি (মডিউল ২-তে বিস্তারিত): প্রতিবার timer বাজলে OS সিদ্ধান্ত নিতে পারে "এবার কি অন্য প্রোগ্রামকে সুযোগ দেবো?"।
🧠 যাচাই করুন
Polling আর interrupt-এর মধ্যে কোনটা দক্ষ, কেন?

Interrupt। Polling-এ CPU বারবার জিজ্ঞেস করে সময় নষ্ট করে; interrupt-এ CPU কাজ করতে থাকে আর দরকার হলে হার্ডওয়্যার তাকে ডাকে।

Timer interrupt না থাকলে কী সমস্যা হতো?

একটা প্রোগ্রাম CPU দখল করে বসে থাকলে (যেমন infinite loop) OS কখনো নিয়ন্ত্রণ ফিরে পেত না — multitasking অসম্ভব হতো।

০৫

OS-এর স্থাপত্য

os-architecture

সব OS একইভাবে বানানো নয়। মূল প্রশ্ন — kernel-এর ভেতরে কতটুকু থাকবে? এই সিদ্ধান্তই monolithic ও microkernel-এর পার্থক্য গড়ে দেয়।

দুটো প্রধান নকশা

MonolithicMicrokernel
kernel-এ কীপ্রায় সব (driver, FS, network)শুধু ন্যূনতম (IPC, scheduling)
গতিদ্রুত (সব একসাথে, সরাসরি ডাক)ধীর (বার্তা পাঠানোর খরচ)
নির্ভরযোগ্যতাএকটা driver ক্র্যাশে পুরো kernel ঝুঁকিতেএকটা সার্ভিস ক্র্যাশ করলেও kernel টিকে থাকে
উদাহরণLinux, বেশিরভাগ UNIXMinix, QNX, seL4
💡 বাস্তবতা — hybrid বিশুদ্ধ কোনোটাই বেশিরভাগ ক্ষেত্রে ব্যবহৃত হয় না। Linux "monolithic" কিন্তু loadable kernel module দিয়ে চলতে চলতে driver যোগ করা যায়। Windows ও macOS মূলত hybrid — কিছু জিনিস kernel-এ, কিছু বাইরে। বাস্তব প্রকৌশল সবসময় বিশুদ্ধ তত্ত্বের চেয়ে ব্যবহারিক সমঝোতা।
🧠 যাচাই করুন
Microkernel-এ একটা driver ক্র্যাশ করলে পুরো সিস্টেম ক্র্যাশ করে না কেন?

কারণ driver kernel-এর বাইরে, user space-এ চলে। তাই সেটা ক্র্যাশ করলে শুধু ওই সার্ভিস বন্ধ হয় (এবং প্রায়ই পুনরায় চালু করা যায়), kernel অক্ষত থাকে।

Monolithic কেন দ্রুত?

সব উপাদান একই kernel space-এ, তাই তারা সরাসরি ফাংশন কল দিয়ে কথা বলে। Microkernel-এ উপাদানগুলো আলাদা, বার্তা (IPC) পাঠিয়ে কথা বলতে হয় — যা ধীর।

০৬

Boot Process — চালু হওয়ার গল্প

boot-process

পাওয়ার বাটন চাপার পর, OS লোড হওয়ার আগে অনেক কিছু ঘটে। এই যাত্রাটা বোঝা জরুরি — কারণ এটাই দেখায় কীভাবে "কিছু নেই" থেকে একটা চলন্ত সিস্টেম তৈরি হয়।

🌅 উপমা — সকালে ঘুম থেকে ওঠা ঘুম থেকে উঠে আপনি একবারে দৌড় শুরু করেন না। প্রথমে চোখ খোলেন (হার্ডওয়্যার চেক), তারপর বিছানা ছাড়েন (bootloader), মুখ ধোন (kernel লোড), জামা পরেন (সার্ভিস চালু), তারপর কাজ শুরু (user login)। কম্পিউটারও ধাপে ধাপে "জাগে"।

চারটা ধাপ

ধাপগুলো বিস্তারিত

১. BIOS/UEFI: মাদারবোর্ডের firmware চালু হয়, হার্ডওয়্যার ঠিক আছে কিনা পরীক্ষা করে (POST — Power-On Self-Test), তারপর কোন disk থেকে boot হবে ঠিক করে।

২. Bootloader: disk-এর নির্দিষ্ট জায়গা থেকে একটা ছোট প্রোগ্রাম (GRUB) চলে, যার একমাত্র কাজ — kernel-কে খুঁজে RAM-এ লোড করা ও তার হাতে নিয়ন্ত্রণ দেওয়া।

৩. Kernel: এবার আসল OS জাগে — memory ব্যবস্থাপনা সেটআপ, driver লোড, scheduler চালু, সব হার্ডওয়্যার প্রস্তুত।

৪. Init: kernel প্রথম user-space প্রোগ্রাম চালায় (Linux-এ systemd, PID 1), যা বাকি সব সার্ভিস (নেটওয়ার্ক, লগইন) চালু করে।

🔬 গভীরে — "bootstrapping" শব্দটা কোথা থেকে "Boot" এসেছে "bootstrapping" থেকে — একটা পুরনো প্রবাদ "নিজের জুতোর ফিতা টেনে নিজেকে তোলা" (একটা অসম্ভব কাজ)। কম্পিউটারের boot ঠিক এই আপাত-অসম্ভব সমস্যা সমাধান করে: OS চালাতে OS দরকar, কিন্তু OS তো এখনো চালু হয়নি! সমাধান — একটা ছোট প্রোগ্রাম একটা বড় প্রোগ্রাম লোড করে, সেটা আরও বড় একটা লোড করে, ধাপে ধাপে। প্রতিটা ধাপ পরেরটাকে "টেনে তোলে"।
🧠 যাচাই করুন
Bootloader-এর মূল কাজ কী?

Disk থেকে kernel খুঁজে RAM-এ লোড করা এবং তার হাতে নিয়ন্ত্রণ হস্তান্তর করা। GRUB একটা সাধারণ উদাহরণ।

Linux-এ প্রথম user-space প্রোগ্রামের PID কত?

PID 1 — সাধারণত systemd (বা পুরনো সিস্টেমে init)। এটাই বাকি সব process-এর পূর্বপুরুষ।

০৭

প্রজেক্ট — strace দিয়ে গোয়েন্দাগিরি

hands-on-strace

এবার তত্ত্ব থেকে বাস্তবে। strace একটা জাদুকরী টুল যা দেখায় একটা প্রোগ্রাম ঠিক কোন কোন system call করছে — অর্থাৎ user/kernel সীমানা কতবার পার হচ্ছে। এটা চালালে এই মডিউলের সব তত্ত্ব চোখের সামনে জীবন্ত হয়ে উঠবে।

🛠 ধাপ ১ — একটা সাধারণ কমান্ড দেখুন টার্মিনালে চালান: 
strace ls
আপনি দেখবেন ls চালাতে কত রকম system call হয় — openat (ফাইল খোলা), read, write (স্ক্রিনে দেখানো), close। একটা সাধারণ কমান্ডের নিচে এত কাজ!
🛠 ধাপ ২ — শুধু গুনে দেখুন 
strace -c ls
-c ফ্ল্যাগ প্রতিটা system call কতবার হলো তার একটা সারাংশ টেবিল দেখায়। কোনটা সবচেয়ে বেশি হচ্ছে লক্ষ্য করুন।

নিজে একটা প্রোগ্রাম লিখে দেখুন

এবার C-তে একটা প্রোগ্রাম লিখে দেখি printf-এর নিচে সত্যিই write() system call ঘটে কিনা:

// hello.c
#include <stdio.h>
#include <unistd.h>

int main() {
    // উপায় ১: printf (ভেতরে buffer করে, তারপর write syscall)
    printf("Hello via printf\n");

    // উপায় ২: সরাসরি write() system call
    write(1, "Hello via write\n", 16);
    //    1 = stdout (screen), 16 = কত byte

    return 0;
}
🛠 ধাপ ৩ — compile করে strace দিয়ে চালান 
gcc hello.c -o hello
strace ./hello
আউটপুটের একদম নিচে দুটো write লাইন খুঁজুন: 
write(1, "Hello via printf\n", 17) = 17
write(1, "Hello via write\n", 16)  = 16
লক্ষ্য করুন — দুটো ভিন্ন উপায়ই শেষ পর্যন্ত একই write() system call-এ পৌঁছেছে! printf শুধু একটা সুবিধাজনক মোড়ক।
🔬 আরও গভীরে — buffering প্রমাণ করুন একটা মজার পরীক্ষা: প্রোগ্রামে অনেকগুলো printf পরপর দিন (newline ছাড়া), তারপর strace করুন। দেখবেন সবগুলো একটাই write()-এ একসাথে গেছে — কারণ printf ডেটা জমিয়ে রেখে একবারে পাঠিয়েছে। এটাই অধ্যায় ৩-এ শেখা buffering, নিজ চোখে দেখা। এভাবে তত্ত্ব ও বাস্তব মিলিয়ে দেখাই সিস্টেম প্রোগ্রামিং শেখার আসল উপায়।
🛠 চ্যালেঞ্জ — নিজে করুন
  1. একটা ফাইল খুলে তাতে কিছু লিখুন (fopen/fwrite), strace করে openat, write, close খুঁজুন।
  2. strace -c দিয়ে ls আর cat-এর system call সংখ্যা তুলনা করুন।
  3. খুঁজে বের করুন: একটা প্রোগ্রাম শুরু হওয়ার সময় কোন system call দিয়ে kernel তাকে চালু করে? (ইঙ্গিত: execve)
🎓 মডিউল ১ শেষ! আপনি এখন জানেন OS কী কাজ করে, kernel ও user space কেন আলাদা, system call কীভাবে সেই সীমানা পার করে, interrupt কীভাবে হার্ডওয়্যারকে সাড়া দিতে দেয়, OS-এর দুই নকশা, আর একটা কম্পিউটার কীভাবে boot করে। আর strace দিয়ে এসব নিজ চোখে দেখেছেন।

এই ভিত্তির উপর দাঁড়িয়ে মডিউল ২ (Process ও Scheduling)-এ ঢুকবো — কীভাবে একটা CPU অনেকগুলো প্রোগ্রামকে একসাথে চালায়, fork/exec কীভাবে কাজ করে, আর নিজের একটা shell বানাবো।
