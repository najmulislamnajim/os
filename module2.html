মডিউল ২ · Virtualizing the CPU

Process ও
Scheduling

একটা CPU, অথচ শত শত প্রোগ্রাম একসাথে চলছে বলে মনে হয়। এই জাদুটা কীভাবে হয়? Process কী, কীভাবে তৈরি হয়, আর OS কীভাবে ঠিক করে কে কখন CPU পাবে — সব এই মডিউলে, নিজের shell বানানো পর্যন্ত।

০০

শুরুর কথা

orientation

মডিউল ১-এ শিখেছি OS কী আর কীভাবে হার্ডওয়্যারের সাথে কথা বলে। এবার প্রথম বড় ধারণা — Virtualization। শুরু CPU দিয়ে: একটা প্রসেসরকে কীভাবে অনেক ভাগে "ভাগ" করে দেখানো হয়।

🧭 এই মডিউল কোথায় ফিট করে OSTEP-এর প্রথম স্তম্ভ Virtualization-এর দুই অংশ: CPU virtualization (এই মডিউল — process, scheduling) আর memory virtualization (মডিউল ৩)। এখানকার মূল প্রশ্ন: একটা মাত্র CPU থাকলেও কীভাবে মনে হয় যে ব্রাউজার, গান, এডিটর সব একসাথে চলছে?
🛠 পরিবেশ মডিউল ১-এর মতোই Linux (বা WSL2) লাগবে। এই মডিউলে অনেক C কোড চালাবেন — gcc থাকলেই যথেষ্ট। প্রজেক্টের জন্য কোনো বাড়তি লাইব্রেরি লাগবে না, সব POSIX system call।
০১

Process আসলে কী?

what-is-a-process

সহজ কথায়, process হলো একটা চলন্ত প্রোগ্রাম। কিন্তু এই পার্থক্যটা গুরুত্বপূর্ণ — প্রোগ্রাম আর process এক জিনিস নয়।

🍰 উপমা — রেসিপি বনাম রান্না একটা রেসিপি (প্রোগ্রাম) হলো কাগজে লেখা নিষ্ক্রিয় নির্দেশনা — disk-এ পড়ে থাকা একটা ফাইল। যখন আপনি সেটা ধরে সত্যিই রান্না শুরু করেন — উপকরণ নেন, চুলা জ্বালান — তখন সেটা একটা process। একই রেসিপি থেকে দুজন একসাথে রান্না করতে পারে (একই প্রোগ্রামের দুটো process), কিন্তু প্রত্যেকের নিজের বাটি, চুলা, অগ্রগতি আলাদা।

একটা process-এর ভেতরে কী থাকে

প্রতিটা process-এর নিজস্ব একটা জগৎ (address space) থাকে। এতে কী কী থাকে:

এছাড়াও OS প্রতিটা process সম্পর্কে কিছু তথ্য রাখে: PID (process ID — অনন্য নম্বর), register-এর মান (program counter সহ — কোন instruction চলছে), খোলা ফাইলের তালিকা, আর বর্তমান অবস্থা। এই সব তথ্য একটা কাঠামোয় রাখা হয় — PCB (Process Control Block)।

📋 PCB — process-এর পরিচয়পত্র OS প্রতিটা process-এর জন্য একটা PCB রাখে — এটাই process-এর সম্পূর্ণ "রেকর্ড"। CPU যখন এক process থেকে আরেকটায় যায়, সে বর্তমান process-এর অবস্থা তার PCB-তে সংরক্ষণ করে আর পরেরটার PCB থেকে অবস্থা তুলে নেয়। Linux-এ এই কাঠামোর নাম task_struct।
🛠 process দেখুন 
ps aux          # চলমান সব process
top             # লাইভ, নিয়মিত আপডেট হয়
ps -ef | grep bash   # নির্দিষ্ট process খোঁজা
প্রতিটা লাইনের শুরুতে PID দেখুন — এটাই ওই process-এর অনন্য পরিচয়।
🧠 যাচাই করুন
প্রোগ্রাম আর process-এর পার্থক্য?

প্রোগ্রাম হলো disk-এ পড়ে থাকা নিষ্ক্রিয় ফাইল (নির্দেশনা)। Process হলো সেই প্রোগ্রামের একটা চলন্ত রূপ — নিজের memory, register, অবস্থা সহ। একই প্রোগ্রাম থেকে অনেক process হতে পারে।

Heap আর stack কোন দিকে বাড়ে?

সাধারণত heap নিচ থেকে উপরে (malloc-এ বাড়ে), stack উপর থেকে নিচে (function call-এ বাড়ে)। মাঝে ফাঁকা জায়গা থাকে যাতে দুটোই বাড়তে পারে।

০২

Process-এর জীবনচক্র

process-states

একটা process সবসময় CPU-তে চলে না। বেশিরভাগ সময় সে অপেক্ষা করে — কখনো CPU-র জন্য, কখনো ফাইল বা নেটওয়ার্কের জন্য। এই অবস্থাগুলো একটা state machine তৈরি করে।

তিনটা প্রধান অবস্থা

এছাড়া দুটো ক্ষণস্থায়ী অবস্থা আছে: New (তৈরি হচ্ছে) আর Terminated (শেষ হয়ে গেছে কিন্তু এখনো পুরোপুরি পরিষ্কার হয়নি)।

🔬 গভীরে — Zombie ও Orphan Zombie: একটা process শেষ হয়ে গেছে, কিন্তু তার parent এখনো তার মৃত্যুর খবর (exit status) নেয়নি (wait() করেনি)। process টা "মৃত" কিন্তু PCB টা রয়ে গেছে — এটাই zombie। খবর নেওয়া হলে পুরোপুরি মুছে যায়।
Orphan: parent আগে মরে গেলে child "অনাথ" হয়ে যায়। তখন init/systemd (PID 1) তাকে দত্তক নেয় আর তার শেষকৃত্য সামলায়।
এজন্যই বাস্তব প্রোগ্রামে parent-কে সবসময় child-এর জন্য wait() করা উচিত — নাহলে zombie জমে।
💡 কেন Blocked অবস্থা এত গুরুত্বপূর্ণ ধরুন একটা process ফাইল পড়তে চাইল — disk ধীর, তাই উত্তর আসতে হয়তো লক্ষ CPU cycle লাগবে। এই সময়টা CPU বসিয়ে রাখা ভয়ংকর অপচয়। তাই OS process-টাকে Blocked করে অন্য process-কে CPU দেয়। I/O শেষ হলে (interrupt দিয়ে খবর আসে) process আবার Ready হয়। এই কারণেই একটা CPU দিয়েও অনেক কাজ একসাথে এগোয় — বেশিরভাগ প্রোগ্রাম বেশিরভাগ সময় I/O-র জন্য অপেক্ষা করে।
🧠 যাচাই করুন
একটা process I/O-র জন্য অপেক্ষা করলে CPU কী করে?

OS ওই process-কে Blocked করে অন্য একটা Ready process-কে CPU দেয়। I/O শেষ হলে প্রথম process আবার Ready হয়। এভাবে CPU বসে থাকে না।

Zombie process কী?

শেষ হয়ে যাওয়া একটা process যার exit status এখনো parent নেয়নি। PCB টা রয়ে গেছে যতক্ষণ না parent wait() করে।

০৩

fork / exec / wait

process-creation

UNIX-এ নতুন process তৈরির পদ্ধতিটা প্রথমে অদ্ভুত লাগে, কিন্তু অসাধারণ মার্জিত। এই তিনটা system call বুঝলে shell কীভাবে কাজ করে তা পরিষ্কার হয়ে যাবে — আর সেটাই আপনার প্রজেক্ট।

fork() — নিজের হুবহু নকল

fork() বর্তমান process-এর একটা প্রায় নিখুঁত কপি তৈরি করে। মূলটা "parent", নতুনটা "child"। দুটোই fork()-এর পরের লাইন থেকে চলতে শুরু করে।

🍴 উপমা — রাস্তার কাঁটা (fork = কাঁটাচামচ/দ্বিধা) fork শব্দের মানে রাস্তার দ্বিধা। এক ব্যক্তি হাঁটতে হাঁটতে একটা জাদুকরী মোড়ে এসে দুজন হয়ে গেল — একই স্মৃতি, একই অবস্থান, কিন্তু এখন দুটো আলাদা মানুষ। শুধু একটা পার্থক্য: একজনের হাতে কাগজে লেখা "তুমি parent", আরেকজনের "তুমি child"। এই কাগজ দেখেই তারা ঠিক করে এরপর কে কী করবে।
// fork-এর মূল ধারণা
#include <stdio.h>
#include <unistd.h>

int main() {
    printf("শুরু: একজন\n");
    int pid = fork();          // এখানে process দুই ভাগ হলো

    if (pid == 0) {
        printf("আমি child\n");       // child-এ fork() ফেরত দেয় 0
    } else {
        printf("আমি parent, আমার child-এর PID %d\n", pid);
    }                             // parent-এ ফেরত দেয় child-এর PID
    return 0;
}
⚠️ fork() একবার ডাকা হয়, দুবার return করে! এটাই সবচেয়ে বিভ্রান্তিকর অংশ। একটা fork() কল, কিন্তু দুটো return — parent-এ child-এর PID, child-এ 0। কারণ কলের পরে দুটো process আছে, দুটোই ওই লাইন থেকে চলছে। এই return মান দেখেই আপনি বোঝেন আপনি কোন process-এ আছেন।

exec() — নিজের খোলস বদলানো

fork শুধু নকল বানায়, কিন্তু আমরা তো নতুন আলাদা প্রোগ্রাম চালাতে চাই। সেটা করে exec() — এটা বর্তমান process-এর memory পুরো মুছে দিয়ে একটা নতুন প্রোগ্রাম সেখানে লোড করে। PID একই থাকে, কিন্তু ভেতরের প্রোগ্রাম সম্পূর্ণ বদলে যায়।

🎭 উপমা — একই অভিনেতা, নতুন চরিত্র exec যেন একজন অভিনেতা এক নাটক শেষ করে সম্পূর্ণ নতুন সাজ-পোশাক-সংলাপ নিয়ে অন্য একটা চরিত্র হয়ে গেল। শরীর (process/PID) একই, কিন্তু ভেতরের সবকিছু (কোড, ডেটা) নতুন। পুরনো কিছুই আর ফিরে আসে না — exec সফল হলে পরের লাইন আর কখনো চলে না।

fork + exec + wait — একসাথে

এই তিনটা মিলেই shell একটা কমান্ড চালায়। প্যাটার্নটা দেখুন — এটাই আপনার প্রজেক্টের মূল:

// একটা কমান্ড চালানোর পূর্ণ প্যাটার্ন
int pid = fork();
if (pid == 0) {
    // child: নিজেকে নতুন প্রোগ্রামে বদলে ফেলো
    char *args[] = {"ls", "-l", NULL};
    execvp("ls", args);
    // exec সফল হলে নিচের লাইন কখনো চলবে না
    perror("exec failed");
} else {
    // parent: child শেষ হওয়া পর্যন্ত অপেক্ষা করো
    wait(NULL);
    printf("child শেষ, আবার prompt দেখাই\n");
}
💡 কেন fork ও exec আলাদা? দুটো এক করে দিলেই তো সহজ হতো? না — আলাদা রাখার একটা চমৎকার সুবিধা আছে: fork ও exec-এর মাঝখানে child কিছু সেটআপ করতে পারে। যেমন — output কে ফাইলে redirect করা (ls > out.txt), বা pipe সেটআপ করা (ls | grep)। এই "মাঝের ফাঁক"-টাই UNIX-এর redirection ও pipe-এর ভিত্তি। প্রজেক্টে এটা কাজে লাগাবেন।
🛠 নিজে চালান উপরের প্রথম fork উদাহরণটা fork.c নামে সেভ করে চালান: gcc fork.c -o fork && ./fork। কয়েকবার চালিয়ে দেখুন — parent আর child-এর প্রিন্টের ক্রম কখনো কখনো বদলে যায়। কেন? কারণ কোনটা আগে চলবে তা scheduler ঠিক করে, আর সেটা অনির্দিষ্ট। এটাই পরের অধ্যায়ের বিষয়।
🧠 যাচাই করুন
fork() child-এ কী return করে?

0। Parent-এ return করে child-এর PID (একটা ধনাত্মক সংখ্যা)। এই পার্থক্য দিয়েই কোড বোঝে সে কোন process-এ আছে।

exec() সফল হলে তার পরের লাইন চলে না কেন?

কারণ exec বর্তমান process-এর পুরো memory (কোড সহ) নতুন প্রোগ্রাম দিয়ে প্রতিস্থাপন করে। পুরনো কোড আর অস্তিত্বেই থাকে না, তাই ফেরার জায়গা নেই।

fork ও exec আলাদা রাখার সুবিধা কী?

মাঝখানে child পরিবেশ সেটআপ করতে পারে — যেমন I/O redirection বা pipe। এটাই shell-এর > ও | এর ভিত্তি।

Context Switch

context-switch

এক CPU, অনেক process। OS দ্রুত একটার পর একটা চালিয়ে ভ্রম তৈরি করে যে সব একসাথে চলছে। এক process থেকে আরেকটায় যাওয়ার এই কৌশলটাই context switch।

👨‍🍳 উপমা — একজন রাঁধুনি, অনেক পদ একজন রাঁধুনি একসাথে ভাত, ডাল, মাংস রাঁধছেন। আসলে তিনি একসাথে করছেন না — ভাত চাপিয়ে ডালে নাড়া দিতে যান, তার আগে মনে রাখেন ভাত কতটুকু হয়েছে। প্রতিটা পদে ফেরার সময় "কোথায় ছিলাম" মনে করেন। CPU-ও তাই — এক process থেকে সরার আগে তার অবস্থা মনে রাখে, পরে ফিরে এসে সেখান থেকে শুরু করে।

Context switch-এ কী ঘটে

OS যখন process A থেকে process B-তে যায়:

  1. A-র বর্তমান অবস্থা (সব register, program counter) A-র PCB-তে সংরক্ষণ করে
  2. B-র PCB থেকে B-র সংরক্ষিত অবস্থা register-এ তুলে আনে
  3. B যেখানে থেমেছিল ঠিক সেখান থেকে চলা শুরু করে
⚠️ Context switch বিনামূল্যে নয় এই সময়টায় CPU কোনো উপকারী কাজ করে না — শুধু অবস্থা সরানো-আনা করে। তাই খুব ঘন ঘন switch করলে সময়ের বড় অংশ শুধু switch-এই চলে যায় (overhead)। আবার খুব কম করলে একটা process অন্যদের অভুক্ত রাখে। এই ভারসাম্যই scheduler-এর মূল চ্যালেঞ্জ। switch-এর সরাসরি খরচ ছাড়াও একটা লুকানো খরচ আছে: নতুন process-এর ডেটা CPU cache-এ না থাকায় শুরুতে ধীর চলে (cache পুনরায় গরম হতে সময় লাগে)।
🔬 গভীরে — কে context switch শুরু করে? দুটো উপায়। Cooperative: process নিজে থেকে ছেড়ে দেয় (system call করলে, বা I/O-র জন্য অপেক্ষায় গেলে)। পুরনো ও ঝুঁকিপূর্ণ — একটা লোভী process কখনো না ছাড়লে সব আটকে যায়। Preemptive (আধুনিক): সেই timer interrupt (মডিউল ১) নিয়মিত OS-কে নিয়ন্ত্রণ ফিরিয়ে দেয়, আর OS জোর করে switch করতে পারে। এজন্যই একটা infinite loop-এ আটকানো প্রোগ্রামও পুরো সিস্টেম জমিয়ে দেয় না — timer এসে OS-কে ডেকে তোলে।
🧠 যাচাই করুন
Context switch-এর সময় CPU কী "উপকারী" কাজ করে?

কিছুই না — এটা বিশুদ্ধ overhead। শুধু এক process-এর অবস্থা সংরক্ষণ ও আরেকটার অবস্থা পুনরুদ্ধার করে। এজন্য অতিরিক্ত switch ক্ষতিকর।

Preemptive scheduling timer interrupt ছাড়া সম্ভব?

না। Timer interrupt ছাড়া OS নিয়ন্ত্রণ ফিরে পায় না, তাই জোর করে process বদলাতে পারে না — তখন শুধু cooperative scheduling সম্ভব।

০৫

CPU Scheduling

scheduling

অনেকগুলো process Ready অবস্থায় CPU চাইছে। OS কাকে আগে দেবে? এই সিদ্ধান্ত নেয় scheduler, আর তার নীতিই ঠিক করে সিস্টেম দ্রুত মনে হবে না ধীর।

🎯 scheduler-এর লক্ষ্য (প্রায়ই পরস্পরবিরোধী) Throughput: একক সময়ে বেশি কাজ শেষ করা। Turnaround time: একটা কাজ জমা থেকে শেষ পর্যন্ত কম সময়। Response time: কি-চাপার পর দ্রুত সাড়া (ইন্টারঅ্যাক্টিভ কাজে জরুরি)। Fairness: কেউ যেন অভুক্ত না থাকে। একটা বাড়ালে আরেকটা কমে — তাই সব scheduler একটা সমঝোতা।

মূল অ্যালগরিদমগুলো

FCFS — First Come First Served

যে আগে আসে, সে আগে পুরো চলে। সহজ, কিন্তু একটা বড় সমস্যা।

⚠️ Convoy effect একটা দীর্ঘ কাজ আগে এলে পেছনের সব ছোট কাজ দীর্ঘক্ষণ অপেক্ষা করে — যেমন সুপারমার্কেটে আপনার সামনে ভরা ট্রলি নিয়ে একজন, আর আপনার হাতে একটা জিনিস। গড় অপেক্ষা অনেক বেড়ে যায়।

SJF — Shortest Job First

সবচেয়ে ছোট কাজ আগে। গড় turnaround time-এর জন্য এটা গাণিতিকভাবে সেরা। কিন্তু সমস্যা — কোন কাজ কত ছোট তা আগে থেকে জানা যায় না, আর একটা দীর্ঘ কাজ চিরকাল অপেক্ষায় থাকতে পারে (starvation)।

Round Robin — সবাইকে সমান টুকরো

প্রতিটা process একটা নির্দিষ্ট সময় (time slice / quantum) পায়, তারপর পেছনে চলে যায়, পরেরজন সুযোগ পায়। Response time-এর জন্য চমৎকার — সবাই দ্রুত একটু একটু করে চলে।

MLFQ — Multi-Level Feedback Queue (বাস্তব সিস্টেমের কাছাকাছি)

বাস্তব OS (Linux, Windows-এর পুরনো সংস্করণ) এমন কিছু ব্যবহার করে। ধারণা: কয়েকটা priority queue, আর process-এর আচরণ দেখে তার priority সমন্বয় করা।

🧠 MLFQ-র চতুর নিয়ম ১. নতুন process সবচেয়ে উঁচু priority-তে ঢোকে।
২. একটা process যদি তার পুরো time slice ব্যবহার করে ফেলে (CPU-লোভী), তাকে নিচু priority-তে নামানো হয়।
৩. একটা process যদি time slice শেষের আগেই I/O-র জন্য ছেড়ে দেয় (ইন্টারঅ্যাক্টিভ), তাকে উঁচুতে রাখা হয়।
ফলাফল: ইন্টারঅ্যাক্টিভ কাজ (টাইপিং, ক্লিক) দ্রুত সাড়া পায়, আর ভারী গণনা পেছনে চলে — অথচ আগে থেকে কিছু জানতে হয় না, আচরণ দেখেই OS শিখে নেয়। মাঝে মাঝে সবাইকে আবার উঁচুতে তুলে (priority boost) starvation ঠেকানো হয়।
অ্যালগরিদমসেরা দিকদুর্বলতা
FCFSসরল, ন্যায্য (ক্রমে)convoy effect
SJFসেরা গড় turnaroundভবিষ্যৎ জানা কঠিন, starvation

🛠 প্রজেক্ট আইডিয়া — scheduler simulator C-তে একটা ছোট প্রোগ্রাম লিখুন যেখানে কয়েকটা "কাজ" (arrival time + burst time সহ) আছে, আর FCFS, SJF, Round Robin প্রতিটার জন্য average waiting time ও turnaround time হিসাব করে তুলনা করুন। এটা scheduling-এর ট্রেড-অফগুলো হাতে-কলমে বুঝিয়ে দেবে।
🧠 যাচাই করুন
Round Robin-এ quantum খুব ছোট হলে সমস্যা কী?

অতিরিক্ত context switch — সময়ের বড় অংশ শুধু switch-এ চলে যায়, আসল কাজ কমে। খুব বড় হলে আবার Round Robin কার্যত FCFS হয়ে যায়।

MLFQ কীভাবে ইন্টারঅ্যাক্টিভ কাজ চেনে — আগে থেকে না জেনেই?

আচরণ দেখে। যে process time slice শেষের আগেই I/O-র জন্য ছেড়ে দেয়, সে সম্ভবত ইন্টারঅ্যাক্টিভ — তাকে উঁচু priority-তে রাখা হয়। CPU পুরো ব্যবহারকারীকে নিচে নামানো হয়।

০৬

Thread — একই process, অনেক সুতো

threads

Process ভারী — প্রতিটার আলাদা memory। কিন্তু কখনো আমরা চাই একই কাজের কয়েকটা অংশ সমান্তরালে চলুক, একই ডেটা ভাগ করে। সেখানেই thread।

🧵 উপমা — এক রান্নাঘরে অনেক রাঁধুনি Process যেন আলাদা আলাদা রান্নাঘর — প্রত্যেকের নিজের সব সরঞ্জাম, একে অপরেরটা দেখতে পায় না। Thread যেন একই রান্নাঘরে কয়েকজন রাঁধুনি — একই সরঞ্জাম ও উপকরণ (memory) ভাগ করে, কিন্তু প্রত্যেকে আলাদা কাজ করে। দ্রুত, কিন্তু সাবধান না হলে দুজন একই ছুরি একসাথে চাইতে পারে (পরের মডিউলের বিষয়)।

Process vs Thread

Thread-রা একই process-এর code, data ও heap ভাগ করে, কিন্তু প্রত্যেকের নিজের stack ও register থাকে (কারণ প্রত্যেকে আলাদা function-এ থাকতে পারে)।

💡 কখন কোনটা? Thread — যখন একই কাজের অংশগুলো ঘন ঘন ডেটা ভাগ করে (যেমন একটা ওয়েব সার্ভারে প্রতিটা request একটা thread)। Process — যখন বিচ্ছিন্নতা ও নিরাপত্তা জরুরি (যেমন ব্রাউজারের প্রতিটা tab আলাদা process, যাতে একটা ক্র্যাশ করলে বাকিগুলো টেকে)। শেয়ার্ড memory-র সুবিধাই thread-এর বিপদ — সেটাই মডিউল ৪ (Concurrency)-এর মূল বিষয়।
🧠 যাচাই করুন
Thread-রা কী ভাগ করে, আর কী আলাদা রাখে?

ভাগ করে: code, global data, heap, খোলা ফাইল। আলাদা: প্রত্যেকের নিজের stack ও register (program counter সহ)।

ব্রাউজার প্রতিটা tab-এ আলাদা process কেন ব্যবহার করে?

বিচ্ছিন্নতা — একটা tab ক্র্যাশ করলে বা কোনো সাইট দূষিত হলে বাকি tab ও পুরো ব্রাউজার নিরাপদ থাকে। thread হলে একটার সমস্যা সবাইকে নামিয়ে দিত।

০৭

IPC — process-রা কীভাবে কথা বলে

inter-process-communication

Process-দের memory আলাদা, তাই তারা সরাসরি একে অপরের ডেটা দেখতে পায় না। কিন্তু প্রায়ই তাদের সহযোগিতা দরকার। OS কয়েকটা উপায় দেয় — এদের একসাথে বলে IPC।

Pipe — shell-এর | এর পেছনে

আপনি যখন ls | grep txt লেখেন, shell একটা pipe তৈরি করে — ls-এর output সরাসরি grep-এর input-এ যায়, disk ছুঁয়ে না গিয়ে। এটা আপনার shell প্রজেক্টের একটা গুরুত্বপূর্ণ অংশ হবে।

🔬 গভীরে — file descriptor redirection এর মূলে আছে UNIX-এর একটা সুন্দর ধারণা: সব কিছুই "file" (file descriptor)। প্রতিটা process-এর তিনটা ডিফল্ট থাকে — 0 (stdin), 1 (stdout), 2 (stderr)। Pipe বানাতে shell একটা pipe তৈরি করে, তারপর dup2() দিয়ে ls-এর stdout-কে pipe-এর লেখার মুখে আর grep-এর stdin-কে pipe-এর পড়ার মুখে "বেঁধে" দেয়। এই fd হেরফেরটাই redirection (>) আর pipe (|) — দুটোরই ভিত্তি। প্রজেক্টে এটাই কাজে লাগাবেন।
🧠 যাচাই করুন
ls | grep txt-এ ডেটা কি disk-এ যায়?

না — pipe সরাসরি ls-এর output grep-এর input-এ পাঠায়, memory-র মধ্য দিয়ে। disk ছোঁয়ার দরকার নেই, তাই দ্রুত।

stdin, stdout, stderr-এর file descriptor নম্বর?

0 = stdin, 1 = stdout, 2 = stderr। redirection ও pipe এই fd গুলো dup2() দিয়ে বদলেই কাজ করে।

প্রজেক্ট — নিজের Shell বানান

build-a-shell

এই মডিউলের সব ধারণা একসাথে জোড়া লাগানোর সময়। একটা shell আসলে একটা সরল কিন্তু গভীর প্রোগ্রাম — এটা বানালে process, fork/exec/wait, pipe, redirection সব পাকা হয়ে যাবে। এটাই সিস্টেম প্রোগ্রামিং-এর ক্লাসিক প্রজেক্ট।

🎯 একটা shell আসলে কী করে একটা লুপ, বারবার: (১) prompt দেখাও, (২) ব্যবহারকারীর লাইন পড়ো, (৩) শব্দে ভাঙো (parse), (৪) fork করে child-এ exec দিয়ে কমান্ড চালাও, (৫) parent-এ wait করো, (৬) আবার শুরু। এটাই REPL (Read-Eval-Print Loop)।

ধাপ ১ — সবচেয়ে সরল shell

// tiny_shell.c — একটা কমান্ড চালাতে পারে
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    char line[1024];
    while (1) {
        printf("myshell> ");              // ১. prompt
        if (!fgets(line, sizeof(line), stdin)) break;  // ২. পড়া (Ctrl+D-তে শেষ)
        line[strcspn(line, "\n")] = 0;      // newline সরাও

        if (strlen(line) == 0) continue;      // খালি লাইন এড়াও
        if (strcmp(line, "exit") == 0) break; // built-in: exit

        // ৩. খুব সরল parse (শুধু কমান্ড, argument ছাড়া আপাতত)
        char *args[] = { line, NULL };

        int pid = fork();                // ৪. fork
        if (pid == 0) {
            execvp(args[0], args);       // child: কমান্ড হয়ে যাও
            perror("exec");              // এখানে এলে exec ব্যর্থ
            exit(1);
        } else {
            wait(NULL);                  // ৫. parent: অপেক্ষা
        }
    }
    return 0;
}
🛠 চালান 
gcc tiny_shell.c -o myshell
./myshell
myshell> ls
myshell> date
myshell> exit
কাজ করছে! এটা fork+exec+wait-এর সরাসরি প্রয়োগ। তবে এখনো argument নিতে পারে না (ls -l চলবে না)।

ধাপ ২ — argument parse করা

লাইনটাকে স্পেস দিয়ে ভেঙে একটা argument array বানাতে হবে। strtok() দিয়ে:

// লাইনকে শব্দে ভাঙা
char *args[64];
int i = 0;
char *token = strtok(line, " ");
while (token != NULL && i < 63) {
    args[i++] = token;
    token = strtok(NULL, " ");
}
args[i] = NULL;                    // execvp-এর জন্য NULL দিয়ে শেষ করা জরুরি
// এখন execvp(args[0], args) দিয়ে "ls -l" ও চলবে

ধাপে ধাপে বাড়ান — চ্যালেঞ্জ

🛠 নিজে যোগ করুন (সহজ থেকে কঠিন)
  1. Built-in cd: cd কেন fork/exec দিয়ে হয় না? (কারণ directory বদলাতে হবে shell-এর নিজের, child-এর নয় — chdir() সরাসরি parent-এ ডাকতে হবে)
  2. Redirection >: ls > out.txt — child-এ exec-এর আগে stdout-কে ফাইলে redirect করুন (open() + dup2())
  3. Pipe |: ls | grep txt — দুটো child, একটা pipe দিয়ে যুক্ত (pipe() + dup2())
  4. Background &: sleep 5 & — parent wait করবে না, prompt সাথে সাথে ফিরে আসবে
  5. একাধিক কমান্ড: ; দিয়ে আলাদা করা কমান্ড পরপর চালানো
🔬 কেন cd built-in হতেই হবে এটা একটা চমৎকার শিক্ষা। আপনি যদি cd-কে fork করে child-এ চালান, তাহলে child-এর directory বদলাবে — কিন্তু child তো সাথে সাথে শেষ হয়ে যায়! parent shell যেখানে ছিল সেখানেই থাকে। তাই cd, exit, export-এর মতো কমান্ডগুলো shell-কে নিজেই চালাতে হয়, fork ছাড়া। এই কারণেই এগুলো "built-in"। ভেবে দেখলে বোঝা যায় — process-এর memory যে আলাদা, তারই সরাসরি পরিণতি এটা।
🛠 আরও এগোতে চাইলে কাজ করা shell হয়ে গেলে যোগ করুন: command history (উপর-তীর দিয়ে আগের কমান্ড), tab completion, environment variable ($HOME), signal handling (Ctrl+C যেন shell বন্ধ না করে শুধু চলমান কমান্ড থামায়)। এগুলো করতে করতে আপনি bash-এর অনেক আচরণ কেন সেভাবে, তা বুঝে যাবেন।
🎓 মডিউল ২ শেষ! আপনি এখন জানেন process কী, তার জীবনচক্র, fork/exec/wait কীভাবে নতুন process বানায়, context switch কীভাবে এক CPU-তে অনেক process চালায়, scheduler কীভাবে সিদ্ধান্ত নেয়, thread ও IPC কী — আর নিজে একটা কাজ করা shell বানিয়েছেন।

পরের ধাপে মডিউল ৩ (Memory ও Virtual Memory) — প্রতিটা process কীভাবে মনে করে তার কাছে পুরো RAM আছে, paging কীভাবে কাজ করে, আর নিজে একটা malloc লিখবেন।
